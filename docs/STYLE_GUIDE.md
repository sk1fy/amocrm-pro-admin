## 1. Принципы

1. **Основной сценарий важнее полноты.** Найти аккаунт → проверить виджеты →
   понять причину → выполнить действие → проверить результат. Любая функция
   оценивается по вкладу в этот путь.
2. **Честные состояния.** «Неизвестно» показывается как неизвестно.
   Отсутствие данных, ноль, устаревшие данные и ошибка источника — четыре
   разных вещи ([states.md](design/states.md)).
3. **Владелец данных меняет данные.** Admin API не пишет в таблицы Core,
   Activity, CRM Events. Core admin вызывает прикладные сервисы Core.
4. **Секреты не покидают сервер.** Ни в ответах, ни в логах, ни в аудите, ни в
   fixtures, ни в документации.
5. **Частичная доступность.** Отказ одного бекенда — деградация его данных, а
   не всей админки.
6. **Небольшие законченные части.** Контракт → бекенд → интерфейс → проверка →
   документация. Незавершённая часть не сливается.

## 2. Порядок работы

Этапы 1–4 завершены. Новая работа — patch-план из
[plan/README.md](plan/README.md), не файлы `plan/stage-*.md`.

Перед частью:

1. Прочитать этот файл, [plan/README.md](plan/README.md), активный
   patch-план, [architecture.md](design/architecture.md),
   [states.md](design/states.md), [data-sources.md](design/data-sources.md),
   [roles.md](design/roles.md).
2. Сверить факты с актуальным `../amocrm-pro` (`git log -1`, миграции,
   `internal/apicontract/routes.go`, `cmd/integrations/main.go`,
   `cmd/activity-control/main.go`, `internal/serviceapi/contracts.go`).
3. Заполнить раздел «Объём» в patch-плане. Расхождения — в план и
   `data-sources.md`.

Внутри части — контракт, бекенд, интерфейс, проверка, документация.
Каждая часть заканчивается зелёным `make check` и обновлённой
документацией.

При сомнении в семантике бекенда — читать код и миграции, а не обзорные
документы: часть документации `amocrm-pro` отстаёт (это сказано в самом
задании и в `docs/project-memory/CONTEXT.md`).

## 3. Репозитории и ветки

| Репозиторий | Что здесь | Правила |
| --- | --- | --- |
| `amocrm-pro-admin` (этот) | Admin API, frontend, deploy, docs | Ветка `main` защищена смыслом: работать в `feature/<stage>-<part>`; сливать после проверок |
| `amocrm-pro` | Core admin read/command listener, контракт, ADR, runbook | Ветка `feature/admin-<тема>`; соблюдать его правила: Docker/Make, ADR для решений, документация на русском, CI должен проходить; не менять поведение публичного API и worker без отдельного обоснования |

Не коммитить в `amocrm-pro/main` напрямую. Не трогать чужие ADR задним числом —
писать новый.

## 4. Go: Admin API и Core admin

Общее с Core (перенимаем его стиль):

- Go версии, указанной в `go.mod` Core (сейчас 1.25); в admin — та же.
- `gofmt`, `go vet` обязательны; `golangci-lint` в admin с базовым набором
  (`errcheck`, `govet`, `staticcheck`, `ineffassign`, `unused`, `gosec`).
- Роутер `github.com/go-chi/chi/v5`, БД `github.com/jackc/pgx/v5`, логи
  `log/slog`, UUID `github.com/google/uuid`. ORM не используются, SQL пишется
  явно.
- Пакеты маленькие, по домену: `auth`, `rbac`, `employees`, `audit`,
  `adapter`, `accounts`, `catalog`, `operations`, `httpapi`,
  `platform/{config,postgres,httpx}`.
- Композиция в `cmd/*/main.go`: загрузка конфигурации → pool → сервисы →
  роутер → `signal.NotifyContext` → graceful shutdown. Бизнес-логика в
  `main` запрещена.
- Контексты и таймауты на каждом внешнем вызове (`context.WithTimeout`);
  таймаут адаптера — из конфигурации бекенда.
- Ошибки: `fmt.Errorf("verb object: %w", err)`, sentinel-ошибки пакета
  (`var ErrNotFound = errors.New(...)`), типизированные ошибки адаптера.
  Сообщение ошибки, попадающее в HTTP-ответ, безопасно (без SQL/DSN/токенов).
- Логи структурные: `logger.Info("http request", "request_id", id, ...)`.
  Не логировать тела запросов, cookies, заголовки авторизации, пароли, токены.
- Конфигурация — только env (в Core так же); отсутствующий обязательный
  секрет → ошибка старта, а не значение по умолчанию. Публичный dev-ключ
  допустим только при `APP_ENV=development`.
- Структуры ответов — отдельные DTO с `json:"snake_case"`; модели БД в JSON не
  сериализуются напрямую.
- Никаких `init()` с побочными эффектами, глобального состояния, `panic` в
  обработчиках.

Core admin (`amocrm-pro/internal/adminread`, `admincommand`):

- Пакет не импортирует `cmd/*`; `cmd/api` импортирует пакет.
- Никаких новых таблиц Core без миграции и ADR.
- Секретные колонки не упоминаются в SQL пакета (проверяется тестом, который
  ищет подстроки `ciphertext`, `webhook_key` в исходниках пакета).
- Прикладные вызовы — те же функции, что CLI: если функции нет — добавить её в
  прикладной пакет (`internal/integrations`, `internal/activitybridge`), а не
  копировать SQL в admin.
- `X-Admin-Actor` → `audit_log.actor_type='admin'`, `actor_id=<значение>`.

## 5. HTTP-контракты

- Версия в пути; изменения обратно совместимы внутри версии.
- Envelope ошибки и правила списков — [admin-api.md](design/admin-api.md#общие-правила).
- Каждый маршрут описан в OpenAPI до реализации обработчика; тест проверяет
  соответствие маршрутов схеме (образец — `api/openapi_test.go` в Core).
- Пагинация — только курсорная (keyset). `OFFSET` запрещён для списков
  больше одной страницы.
- Лимиты: `limit` по умолчанию 25, максимум 100; окно времени для jobs — не
  более retention Core (7 суток).
- `GET` не имеет побочных эффектов; проверки с внешними вызовами — `POST` и
  операция.
- Заголовки: `X-Request-ID` (приём/возврат), `Idempotency-Key` (мутации),
  `X-Requested-With: admin-ui` (мутации из браузера), `X-Admin-Actor` (Admin
  API → Core).
- Время — RFC 3339 UTC; frontend переводит в локальный часовой пояс.

## 6. PostgreSQL и миграции

- PostgreSQL 17, как в Core.
- Миграции — `backend/migrations/NNNNNN_name.up.sql` и `.down.sql`, обе
  обязательны, down проверяется в тесте. Нумерация сквозная, без пропусков.
- Все таблицы: `id` (UUID или BIGSERIAL по смыслу), `created_at`,
  `updated_at` с триггером `set_updated_at()` (как в Core), `CHECK` на
  перечисления статусов, `NOT NULL` по умолчанию.
- Индексы под каждый фильтр списка и под keyset-курсор.
- Секреты в admin DB: только хеши (`token_hash`, `password_hash`).
- Запросы к БД — с таймаутом контекста; транзакции — короткие, без внешних
  вызовов внутри.
- Никогда не выполнять `down` на общих данных без явного подтверждения
  (перенять `MIGRATION_DOWN_CONFIRM` из Core).

## 7. Frontend

- TypeScript `strict`, ESLint (`typescript-eslint`, `react-hooks`,
  `jsx-a11y`), Prettier. `any` запрещён, `unknown` + сужение.
- Структура:

  ```text
  frontend/src/
    app/            роутер, провайдеры, layout
    api/            клиент, типы ответов (генерируются из OpenAPI или пишутся вручную и проверяются тестом контракта)
    features/       overview, accounts, connections, integrations, operations, system, auth
    components/     StatusBadge, Observation, DataTable, FilterBar, EmptyState, ErrorState, SourcesBanner, IncidentBanner, ActionMenu, CopyableId
    states/         словарь состояний: константы, тексты, тона (единственное место)
    lib/            утилиты (форматирование времени, нормализация)
  ```

- URL — источник истины для фильтров, сортировки, курсора, вкладок. Локальное
  состояние только для черновиков форм.
- Query keys включают все параметры запроса; мутации инвалидируют затронутые
  ключи.
- Отображение состояния — только через `StatusBadge`/`Observation` со
  значениями из `states/`. Строковые статусы бекенда в JSX запрещены.
- Каждый блок данных бекенда показывает `observed_at` (подсказка или подпись)
  и особый вид для `stale`/`unavailable`/`unknown`.
- `null` → «—», `0` → «0». Никаких `value || '—'`.
- Тексты интерфейса — русский, без жаргона в пользовательских строках
  (допустимы термины amoCRM: OAuth, webhook, job — с пояснением в подсказке).
- Доступность: семантические элементы, `aria-label` у иконок, фокус в
  диалогах, работа с клавиатуры в таблицах и фильтрах.
- Стили — CSS Modules и переменные из `app/theme.css`; глобальные стили
  только для reset и переменных. UI-киты и CSS-фреймворки не подключаются.
- Диалог команды всегда показывает: объект, область воздействия,
  необратимость, следующий шаг для клиента (если есть).

## 8. Состояния, наблюдения, свежесть

- Канонические состояния — только из [states.md](design/states.md). Новое
  состояние сначала добавляется туда (с тоном, текстом, правилом), затем в код.
- Маппинг бекенд → канон живёт в адаптере и покрыт табличным тестом, включая
  неизвестное значение → `unknown` + `raw`.
- Агрегаты (состояние аккаунта) считаются в Admin API и всегда сопровождаются
  разбивкой.
- Данные, полученные от бекенда, возвращаются как `Observation`; список — с
  `sources[]`.
- Свежесть определяет Admin API; frontend не «угадывает» свежесть по времени.
- Слова «синхронизировано», «подключено», «работает» в интерфейсе допустимы
  только для состояний, подтверждённых источником с `observed_at`.

## 9. Безопасность

- Ответы и логи не содержат: OAuth access/refresh tokens, client secrets,
  webhook keys/URL с ключами, `ENCRYPTION_KEYS`, `ADMIN_API_TOKEN`, cookie
  сессий, пароли, `payload`/`result` jobs до отдельного решения о редакции.
  Автотест рекурсивно проверяет ключи JSON-ответов на подстроки `secret`,
  `token`, `ciphertext`, `key_hash`, `password` (кроме полей запроса на вход
  и создание).
- Права проверяются на сервере на каждом запросе по БД; frontend только
  скрывает.
- Мутации: сессия + `X-Requested-With` + `Origin` + `Idempotency-Key`.
- Cookie `HttpOnly; Secure; SameSite=Strict`. В development `Secure`
  отключается только при `APP_ENV=development`.
- Ограничение частоты входа; одинаковый ответ на любую ошибку входа.
- Admin listener Core и Admin API management listener слушают только
  loopback/внутреннюю сеть. Публикация портов в compose — `127.0.0.1:`.
- Fixtures и тесты используют только вымышленные домены (`*.example.invalid`,
  `example.amocrm.ru` недопустимо, если домен может совпасть с реальным —
  использовать `fixture-<n>.amocrm.test`) и вымышленные ID.
- Зависимости — только с фиксированными версиями в lockfile; обновления
  отдельными коммитами.

## 10. Операции и команды

- Команда возвращает `202` с `operation{id, state, target, command}`;
  состояние опрашивается по `GET /operations/admin/{id}`.
- `Idempotency-Key` обязателен; повтор с тем же ключом и payload → тот же
  результат; с другим payload → `conflict`.
- Перед выполнением — чтение текущего состояния объекта и проверка
  предусловия; ошибка предусловия Core показывается как есть (безопасно).
- Обрыв соединения → `unknown_outcome`, интерфейс предлагает проверить
  объект, а не повторить слепо.
- Семантику Core не переименовывать: `revoke` — локальная инвалидация,
  `uninstall` может быть частичным, `disable` интеграции ≠ `disable`
  установки.
- Повтор разрешён только для команд с определённой безопасной семантикой
  (список в ADR).
- Аудит: в admin DB (кто, что, над чем, результат, безопасный diff) и в Core
  (`X-Admin-Actor`).

## 11. Тесты и проверки

`amocrm-pro` — строго по его Makefile: `make fmt-check vet test openapi-check
integration-test`; Activity-части — `make activity-ci`. Host Go там не
используется.

`amocrm-pro-admin` — Docker-first, `make check` объединяет:

| Цель | Что делает |
| --- | --- |
| `make lint` | `gofmt -l`, `go vet`, `golangci-lint`; `npm run lint`, `tsc --noEmit` |
| `make test` | `go test -race ./...`; `npm test` (Vitest) |
| `make integration-test` | миграции up/down и `*_integration_test.go` с PostgreSQL в изолированном compose-проекте |
| `make e2e` | Playwright против собранного стека с fixture-адаптером |
| `make check` | всё выше |

Правила:

- Каждая часть добавляет тесты трёх уровней там, где применимо: unit
  (маппинг, нормализация, RBAC-таблица), integration (SQL, миграции), e2e
  (сценарий экрана).
- Тесты частичной доступности обязательны: адаптер с ошибкой, адаптер с
  таймаутом, адаптер без возможности.
- Табличные тесты для словаря состояний и матрицы прав генерируются из
  констант, чтобы документация и код не расходились (тест сравнивает список
  прав в коде с таблицей `roles.md` — парсинг markdown допустим).
- Fixtures в тестах — вымышленные; SQL-fixture для dev-стека помечен
  `origin=fixture`.
- Временные скрипты проверки держать вне репозитория (`/tmp`), не коммитить.

## 12. Документация

- Язык — русский; код, идентификаторы, имена файлов, коммиты — английский.
- Markdown, строки до 80 символов, таблицы для матриц и словарей.
- Каждое архитектурное решение — ADR `docs/adr/NNNN-slug.md` с разделами
  Контекст, Решение, Отклонённые варианты (если были), Последствия. Нумерация
  сквозная. ADR не редактируются задним числом — новый ADR отменяет старый.
- Обязательные обновления при изменениях:

  | Изменение | Обновить |
  | --- | --- |
  | Новое поле интерфейса | `design/data-sources.md` |
  | Новое состояние или правило показа | `design/states.md` |
  | Новый маршрут | OpenAPI + `design/admin-api.md` |
  | Новое право | `design/roles.md` |
  | Новый экран/маршрут UI | `design/screens.md` |
  | Изменение адаптера | `design/backend-adapter.md` |
  | Изменение в `amocrm-pro` | ADR и runbook там, ссылка отсюда |

- Не писать документацию о том, что не реализовано, как о реализованном.
  Планируемое — в `plan/`, сделанное — в `design/` и runbooks.
- Runbooks (`docs/runbooks/`): `local-run.md` (разработка),
  `operator.md` и `new-module.md` (эксплуатация). `demo-stage-N.md` —
  исторические сценарии приёмки этапов; актуальный сквозной путь —
  `operator.md` и `demo-stage-4.md`.
- Индекс папки — [README.md](README.md).

## 13. Коммиты и PR

- Формат: `<scope>: <imperative summary>` на английском, как в Core
  (`fix: address …`, `docs: clarify …`, `deploy: track …`). Scopes:
  `admin-api`, `frontend`, `adapter`, `deploy`, `docs`, `core-admin` (для
  `amocrm-pro`).
- Один коммит — одна законченная мысль; форматирование отдельно от логики.
- Описание PR: что сделано, как проверено (команды и результат), что не
  сделано, ссылки на разделы плана.
- Не сливать при красных проверках; не отключать тесты «временно».
- В `amocrm-pro` PR дополнительно указывает: изменённые контракты, миграции,
  влияние на публичный API/worker (по умолчанию «нет», иначе обосновать).

## 14. Запрещено

- Laravel, Filament, PHP-код, перенос структуры разделов старой админки.
- Запуск CLI (`integrations`, `activity-control`, `docker`, `psql`) через
  `os/exec` из веб-запросов.
- Прямое подключение Admin API к PostgreSQL Core/Activity/CRM Events (чтение
  или запись).
- `SELECT *`, чтение секретных колонок, возврат `payload`/`result` jobs без
  решения о редакции.
- Redis и другие новые инфраструктурные зависимости без ADR.
- Идентификаторы аккаунтов/установок/сотрудников в labels Prometheus.
- «Умолчания вместо данных»: `status ?? 'active'`, `count || 0` для
  отсутствующих значений.
- Скрытые fallback: если бекенд недоступен — показать `unavailable`, а не
  кеш без пометки и не пустой список как «нет подключений».
- Изменение семантики команд Core при отображении («revoke» как «отзыв в
  amoCRM»).
- Хранение паролей, токенов, ключей в репозитории, `.env` в git, реальные
  домены/ID клиентов в fixtures и документации.
- Пустые каталоги-заготовки, `TODO` без ссылки на пункт плана, закомментированный код.

## 15. Определение готовности части

Часть готова, когда:

- [ ] Контракт описан в OpenAPI и `design/admin-api.md`, тест соответствия
      зелёный.
- [ ] Бекенд реализован, unit + integration тесты зелёные.
- [ ] Интерфейс реализован, состояния показываются по словарю, e2e сценарий
      (если есть экран) зелёный.
- [ ] `data-sources.md`, `states.md`, `roles.md`, `screens.md` обновлены по
      таблице раздела 12.
- [ ] Автотест на отсутствие секретов в ответах покрывает новые маршруты.
