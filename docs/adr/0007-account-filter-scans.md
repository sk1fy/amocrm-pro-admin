# ADR-0007. Ограниченный скан для фильтров списка аккаунтов

## Контекст

Core admin listener отдаёт страницы аккаунтов по keyset-курсору, а часть
фильтров Admin API (`product`, `connection`, `problem`, `origin`) вычисляется
уже после агрегации в Admin API: их нет в контракте Core. Фильтрация после
постраничной выборки давала неверные счётчики и пустые страницы: при
`limit=1` и `problem=reauth_required` ответ мог быть пустым, хотя совпадения
есть, а блок «Требуют внимания» показывал нули. При этом с версии списка
Core 2026-09-13 установки несут `webhook_status`, `authorization_state` и
`recent_failed_jobs`, поэтому все проблемы вычисляются в Admin API без
дополнительных запросов.

Курсор в Admin API — непрозрачная строка; контракт не обещает его формат.

## Решение

Если активен хотя бы один пост-фильтр (`product`, `connection`, `problem`,
`origin`), `accounts.Service` выполняет ограниченный скан:

- страницы по 100 аккаунтов с каждого бекенда, не более 10 страниц и 1000
  аккаунтов суммарно;
- найденные аккаунты сливаются, дедуплицируются, фильтруются и сортируются
  до пагинации;
- `total` заполняется, только если скан дошёл до конца и все источники
  доступны; иначе `null` (интерфейс показывает «—» или длину страницы);
- для продолжения выдаётся курсор `scan:<offset>`; при следующем запросе
  скан повторяется с самого начала и пропускает `offset` совпадений;
- без пост-фильтров поведение прежнее: прямой запрос страницы к бекендам и
  keyset-курсоры по каждому бекенду, `total` — сумма `total` бекендов.

Формат курсора `scan:<offset>` видит только frontend.

## Отклонённые варианты

- **Фильтры проблем в Core.** Словарь состояний и правила агрегации —
  канонические сущности Admin API ([states.md](../design/states.md));
  перенос их в Core размазал бы правила по двум репозиториям.
- **N+1-обогащение страницы списка через карточки установок.** Дороже скана
  и не решает фильтрацию до пагинации.
- **Неограниченный скан.** На больших установках превращается в отказ
  обслуживания; лимит 1000 аккаунтов выбран по пилотному масштабу.
- **Offset-курсор для всех списков.** Keyset-курсоры бекендов стабильнее;
  offset применяется только там, где без скана не обойтись.

## Последствия

- Фильтрованный список дороже нефильтрованного: до 10 страниц к каждому
  бекенду на запрос. При выходе за лимит скана `total` и продолжение не
  выдаются — это честная деградация, зафиксированная в интерфейсе.
- Смена фильтра обязана сбрасывать курсор (frontend уже сбрасывает
  `cursor` при изменении любого фильтра).
- Если источник недоступен, `total` не вычисляется: частичные данные нельзя
  выдавать за полный счётчик.
- При появлении серверных фильтров в Core этот механизм можно удалить без
  изменения контракта Admin API.
