# ADR-0014: Retention и объём admin DB

Статус: принято, 2026-09-13.

## Контекст

Этап 4 вводит постоянную эксплуатацию Admin API. В admin DB растут
три журнальные таблицы: `admin_audit_log` (аудит действий сотрудников
и входов), `operations` (устойчивые операции этапа 2) и `sessions`
(сессии входа). Без политики удаления они растут бессрочно: аудит —
на каждое изменение сотрудника, доступа и команду, операции — на
каждый запуск команды, сессии — на каждый вход.

[STYLE_GUIDE](../STYLE_GUIDE.md) (§6) требует индексы под запросы,
короткие транзакции и парные миграции `up`/`down`. Управляемого
планировщика задач в Admin API нет: сервис не должен выполнять
разрушительные удаления самостоятельно, решение об удалении
принимает оператор.

## Решение

1. Политика хранения:
   - `admin_audit_log` — 365 суток. Кто менял сотрудников, доступ и
     команды, должно быть доступно год.
   - `operations` — 180 суток, только терминальные состояния
     (`succeeded`, `failed`, `partial`, `unknown_outcome`).
     Незавершённые (`accepted`, `pending`, `running`) не удаляются
     никогда, независимо от возраста.
   - `sessions` — истёкшие или отозванные старше 30 суток.
     Действующие сессии не удаляются: условие по `expires_at`
     дополнительно ограничено `now()`, поэтому даже дата отсечения
     в будущем не ломает поиск активной сессии.
2. Индексы. `admin_audit_log` уже имеет
   `admin_audit_created_id_idx (created_at DESC, id DESC)`: ведущая
   колонка `created_at` обслуживает условие `created_at < $1`, новая
   миграция не нужна. Для операций миграция
   `000006_retention_indexes` добавляет частичный индекс
   `operations_terminal_updated_idx (updated_at) WHERE state IN
   ('succeeded','failed','partial','unknown_outcome')` — он повторяет
   предикат удаления и не растёт на незавершённых операциях.
3. Интерфейс удаления — только `admin-cli prune` (запуск из внешнего
   cron). Флаги `--audit-before`, `--operations-before`,
   `--sessions-before` принимают RFC 3339 или `YYYY-MM-DD` (UTC);
   таблица без флага пропускается, хотя бы один флаг обязателен.
   Режим по умолчанию — dry-run: печатает число подходящих строк и
   ничего не удаляет. Удаление — только с явным `--confirm`. DSN и
   секреты не печатаются.
4. Аудит удаляется по возрасту и не зависит от наличия сотрудника:
   строки аудита самостоятельны и сохраняются, пока не истёк срок.
5. Транзакции короткие: каждый шаг — один `DELETE` (или `count(*)`
   в dry-run) с таймаутом контекста, без внешних вызовов. Фоновая
   очистка сессий в Admin API (`Service.Cleanup`) переиспользует
   `PruneExpiredBefore` и не дублирует предикат.

## Отклонённые варианты

- Планировщик внутри Admin API: сервис получил бы право
  разрушительных удалений, а несколько реплик дублировали бы работу.
  Внешний cron проще, наблюдаемее и не требует распределённой
  блокировки.
- Удаление по умолчанию без dry-run: случайная дата уничтожала бы
  историю; dry-run с `--confirm` оставляет решение оператору.
- Автоматические даты отсечения «от now»: скрытая логика вместо
  явного решения; политика печатается как help-текст команды.
- Удаление операций по `created_at`: долгая операция обновляется
  позже, и удаление по возрасту создания потеряло бы актуальный
  результат; поэтому `updated_at`.
- Единый индекс `operations(updated_at)`: он рос бы на незавершённых
  операциях; частичный индекс дешевле и точнее.
- Удаление аудита вместе с сотрудником: аудит — независимый журнал,
  его строки не удаляются при отключении сотрудника.
- Хранение агрегатов статистики в admin DB: живые запросы Core —
  источник ([ADR-0010](0010-stage-3-activity-stats.md)), собственных
  агрегатных таблиц нет.

## Последствия

Оценки объёма (допущения; фактические числа замеряются в пилоте):

| Таблица | Строк/сутки | Строк/год | Строка | Размер/год |
| --- | --- | --- | --- | --- |
| admin_audit_log | ~2 000 | ~730 000 | ~0.5–1 КиБ | ~0.4–0.7 ГиБ |
| operations (термин.) | ~300 | ~110 000 | ~1–2 КиБ | ~0.1–0.2 ГиБ |
| sessions | ~50 | ~18 000 | ~0.2 КиБ | ~4 МиБ |
| Итого | ~2 350 | ~860 000 | | ~0.5–1 ГиБ |

`operations` хранит не более 180 суток, `sessions` — 30; строка «за
год» показывает годовой поток для полноты оценки. Числа обязаны быть
перемерены на пилотных данных: интенсивность команд и средний размер
`result`/`metadata` сильнее всего влияют на оценку.

Регулярность и наблюдаемость: prune запускается внешним cron (например,
раз в сутки ночью) с датами в прошлом. Сначала dry-run, затем тот же
вызов с `--confirm`. Ненулевой код возврата cron должен алертить.
Пример и порядок — в `docs/design/admin-db-schema.md` и runbook
оператора.

Стоимость: частичный индекс незначительно замедляет вставку
терминальных операций. `DELETE` освобождает страницы для повторного
использования, но не уменьшает файл; при объёме меньше 1 ГиБ в год
штатного autovacuum достаточно. Резервное копирование (часть 4.3)
наследует политику.
