# ADR-0009: устойчивые операции и диагностика

Статус: принято. Дата: 2026-09-13.

## Контекст

Команда должна иметь доступный после перезагрузки результат. Разрыв HTTP
не доказывает отсутствие эффекта. Секрет создания/ротации интеграции нельзя
сохранять для фонового повторного исполнения.

## Решение

Admin DB хранит `operations` (миграция 000004). Идемпотентность общая для
сотрудников в области `(backend,target_type,target_id,command,key)`.
Хеш канонического JSON-запроса включает все значения, включая секрет,
но тело запроса и секрет не сохраняются. Другой payload с тем же ключом
даёт conflict. Частичный unique-index запрещает одновременно активные
операции одного объекта. Повтор исходного запроса возвращает прежнюю
операцию, а не проверяет повторно уже изменённое состояние объекта.

Admin передаёт свой UUID операции как `Idempotency-Key` Core.
Core использует его как UUID квитанции. Поэтому после потери ответа
достаточно `GET /admin/v1/commands/{uuid}`; повтор POST не требуется.
`request_key` списка Admin позволяет браузеру найти операцию, даже если
ответ с её UUID не был получен. В браузере хранятся только UUID и контекст
объекта, без тела команды. При unknown_outcome повтор эффекта запрещён:
нужно прочитать результат или проверить объект.

Приём и конечное состояние операции записываются атомарно с аудитом Admin.
Аудит содержит инициатора, request_id, объект, команду, результат и имена
изменяемых полей. Значения client_secret не сохраняются ни в operations,
ни в аудите. Core ведёт свой аудит с actor_type=admin и X-Admin-Actor.

Роль читается из БД перед приёмом и снова после чтения предусловий,
непосредственно перед dispatch. Core проверяет предусловия ещё раз
под транзакционными блокировками. Сбой чтения до dispatch — failed;
неопределённый транспортный исход после отправки — unknown_outcome.
Принятый dispatch завершается в ограниченном контексте даже после ухода
браузера. После аварии процесса истёкшая lease становится unknown_outcome;
система никогда не восстанавливает отсутствующий payload повторным POST.

Core сохраняет отдельные durable receipts. Check и внешний этап uninstall
выполняет worker через существующий исходящий бюджет. Pending-квитанции
опрашиваются при чтении операции и фоновым reconciler каждые 10 секунд.
Это опрос уже запущенных Core jobs, а не второй исполнитель команд.
Подтверждённое терминальное состояние нельзя заменить запоздалым poll.

Состояния отражают этап: accepted/running при приёме и dispatch, pending
при ожидании backend job; succeeded/failed/partial/unknown_outcome — исход.
Негативная классификация проверки OAuth не означает сбой исполнения
операции: succeeded + classification=auth_error означает завершённую
диагностику с отказом авторизации.

Последняя диагностика представлена отдельным authorization_check Observation
в карточке подключения. observed_at относится к внешнему вызову, не к
моменту чтения карточки. Через 15 минут результат помечается stale.
Исходные факты credentials не заменяют результат этой проверки.

## Безопасные повторы

Разрешены только webhook.reconcile и widget.ping в failed/dead.
Core дополнительно требует активные установку и интеграцию и проверяет
лимит попыток. retry_allowed/retry_reason в Core Job — источник разрешения;
Admin не расширяет allowlist. Lead-status, обработка исторических событий
и произвольные jobs остаются read-only. Activity delivery retry требует
failed, срок менее 7 суток и принадлежность указанной установке.

Partial uninstall можно повторить новым ключом после явного подтверждения.
Он продолжает восстановление уже зафиксированного локального uninstall.
Старый ключ всегда возвращает прежний partial-результат.

## Последствия

Нужны миграции Admin и Core перед запуском новых API/worker.
Существующие команды CLI сохраняются. Прямого доступа Admin к Core DB нет.
Реальные OAuth-проверки требуют живых credentials; fixture показывает
отмеченный тестовый результат и не обращается в amoCRM.
