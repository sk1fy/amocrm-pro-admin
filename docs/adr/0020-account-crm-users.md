# ADR-0020: Пользователи amoCRM в карточке аккаунта

Дата: 2026-11-06. Статус: принято.

## Контекст

Карточке аккаунта нужна вкладка со списком пользователей amoCRM: ID, имя,
активность и признак администратора. До этой части в
[data-sources.md](../design/data-sources.md) было записано, что надёжного
источника нет. Core хранит `installations.installed_by`, но не заполняет
его, а контакты из формы установки виджета (имя, телефон, роль) — другая
сущность, Core её не хранит. Пользователей amoCRM Core уже читает для
TeamOS и распределения. Читает их worker — единственный процесс Core,
который ходит в amoCRM (ADR-0042 в `amocrm-pro`).

[ADR-0017](0017-connection-state-freshness.md) отклонил проверку amoCRM
при каждом GET интерфейса: там речь о фоновом обновлении списков и
состоянии авторизации на каждом экране.

## Решение

1. Опциональный интерфейс адаптера `CRMUsersBackend` с
   `GetCRMUsers(ctx, actor, accountID)` и `CRMUsersTimeout()`. Возможность
   `crm-users` проверяется через `AsCRMUsers`. Модель
   `CRMUsers{State, Connection, FreshUntil, RetryAfter, Users, Total}`,
   пользователь — `{ID, Name, IsActive, IsAdmin}`. Email, телефон, группа,
   роль и права в контракт не входят.
2. Core-адаптер объявляет `crm-users`, только если задан `crm_base_url`:
   это listener worker `core-admin-crm:8085`, токен общий с
   `base_url`. `crm_timeout` по умолчанию 10s, максимум 12s, чтобы
   ответить раньше `WriteTimeout` 15s Admin API. Для чтения из amoCRM
   нужен отдельный бюджет: `GatherWithin` берёт таймаут из возможности,
   а не из дескриптора (5s).
3. Ответ Core 200 — всегда наблюдение `fresh` с `data.state`. Состояния
   `ok`, `no_authorized_connection`, `auth_error`, `rate_limited`,
   `incomplete`, `network_error`, `internal_error`; неизвестное значение
   → `unknown` + `raw`. Список и `total` есть только при `ok`. В
   остальных состояниях `users: null` означает, что список неизвестен.
   Пустой массив означает аккаунт без пользователей. Недоступный или
   медленный Core — источник `unavailable`, ошибка списка не подменяет.
4. `GET /api/v1/accounts/{account_id}/crm-users` под `accounts:read`,
   ответ `{items, sources}` как у подписки, `Cache-Control: no-store`.
   Admin API ничего не кэширует. Снимок держит Core: до 5 минут, не
   больше 1000 пользователей (четыре страницы amoCRM), без пагинации.
5. Вкладка «Пользователи» читает список при открытии и по кнопке
   «Обновить». Ключ запроса не входит в polling и не обновляется по
   фокусу, `staleTime` — 60 секунд.

## Отклонённые варианты

- Строить вкладку «Контакты» на `installed_by`: Core поле не пишет, а
  контакты из формы установки — другая сущность без источника.
- Читать amoCRM из Admin API или admin listener процесса `api`: второй
  владелец OAuth-токенов и бюджета amoCRM.
- Хранить список в Admin DB или фоново обновлять его: персональные данные
  в ещё одной базе и запросы к amoCRM без открытой вкладки.
- Polling вкладки: каждые 15 секунд UI запрашивал бы снимок, который
  Core обновляет раз в 5 минут.

## Последствия

Открытие вкладки может вызвать до четырёх запросов к amoCRM на аккаунт за
пять минут. Это чтение по явному действию сотрудника, а не фоновая
проверка ADR-0017. Без `crm_base_url` или со старым Core вкладка честно
показывает, что данных нет. Отказ amoCRM виден как состояние со
списком `null`, а не как пустой список. Email и телефоны пользователей,
а также контакты установки требуют отдельного решения об источнике и
доступе.
