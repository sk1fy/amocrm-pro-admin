# ADR-0003: Вход сотрудников, сессии и роли

Статус: принято. Дата: 2026-09-12.

## Контекст

Инициатор каждого действия должен определяться сервером по сессии сотрудника.
Внешнего SSO у команды пока нет; круг сотрудников ограничен.

## Решение

- **Учётные записи** хранятся в admin PostgreSQL: `employees(id, email, name,
  role, password_hash, status, created_at, updated_at)`. Пароли — argon2id
  (`golang.org/x/crypto/argon2`), параметры фиксируются в коде и версионируются
  в хеше.
- **Сессии** — серверные, в таблице `sessions(id, employee_id, token_hash,
  created_at, last_seen_at, expires_at, revoked_at, ip, user_agent)`. Клиенту
  выдаётся случайный токен в cookie `admin_session`; в БД хранится только
  SHA-256 хеш. Cookie: `HttpOnly; Secure; SameSite=Strict; Path=/`.
- **Сроки**: абсолютный 12 часов, простой 2 часа (настраиваются env).
  Смена роли или блокировка сотрудника отзывает все его сессии; проверка
  роли выполняется по БД на каждом запросе, не по данным в cookie.
- **CSRF**: `SameSite=Strict` + обязательный заголовок
  `X-Requested-With: admin-ui` на всех методах, кроме GET/HEAD/OPTIONS, +
  проверка `Origin` против настроенного `ADMIN_PUBLIC_ORIGIN`.
- **Роли**: `viewer`, `operator`, `admin` — матрица в
  [roles.md](../design/roles.md). Права проверяются на сервере в middleware
  `rbac.Require(permission)`; frontend лишь скрывает недоступные действия.
- **Первый администратор** создаётся через `admin-cli employee create
  --email … --role admin --password-stdin`. Env-bootstrap не используется, чтобы
  пароль не жил в конфигурации.
- **Аудит**: вход, выход, неуспешные попытки (без пароля), отзыв сессий,
  изменения сотрудников — в `admin_audit_log`.

## Отклонённые варианты

- JWT в cookie без серверного состояния — нельзя отозвать доступ немедленно.
- OAuth через amoCRM — сотрудник админки и пользователь amoCRM разные сущности;
  привязка к аккаунту amoCRM не нужна и опасна.
- SSO (Google/Yandex) — возможен позже как дополнительный способ входа; таблица
  `employees` оставляет поле `password_hash` nullable для этого.

## Последствия

- Ограничение частоты попыток входа по IP и email (in-memory, bounded), ответ на
  неверные данные без различия «нет пользователя»/«неверный пароль».
- Сессии чистятся фоновой задачей admin-api порциями.
