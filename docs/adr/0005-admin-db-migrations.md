# ADR-0005: Миграции admin DB

Статус: принято. Дата: 2026-09-12.

## Контекст

Admin API владеет собственной PostgreSQL ([admin-db-schema.md](../design/admin-db-schema.md)).
Нужен способ применять миграции в Docker-first workflow, совместимый с CI и с
правилом «down только с явным подтверждением». Core использует собственный
мигратор `cmd/migrate` с таблицей `schema_migrations`, хранящей контрольные
суммы up/down файлов.

## Решение

- Формат файлов — как в Core: `backend/migrations/NNNNNN_name.up.sql` и
  `.down.sql`, обе части обязательны, нумерация сквозная без пропусков.
- Мигратор — `backend/cmd/admin-migrate`, собственная реализация на pgx
  (~200 строк): читает каталог, проверяет непрерывность номеров, применяет
  каждую миграцию в транзакции, пишет `schema_migrations(version, name,
  checksum, down_checksum, applied_at)`, проверяет контрольные суммы уже
  применённых файлов, берёт `pg_advisory_lock` на время прогона.
- `down` требует `MIGRATION_DOWN_CONFIRM=revert-all-migrations` (как в Core)
  и откатывает **все** миграции в обратном порядке; частичный откат не
  поддерживается.
- Integration-тест мигратора: `up` → проверка количества строк и наличия
  таблиц → неподтверждённый `down` отклоняется → подтверждённый `down` →
  таблицы отсутствуют → два параллельных `up` дают одно применение.

## Отклонённые варианты

- `golang-migrate/migrate` — умеет всё нужное, но добавляет зависимость с
  собственными правилами именования, не проверяет down-checksum и требует
  отдельной обёртки для подтверждения down. Разница в объёме кода невелика,
  а единообразие с Core важнее.
- Миграции внутри процесса `admin-api` при старте — размывает границу между
  owner и runtime ролями и мешает нескольким репликам.

## Последствия

- Compose содержит сервис `migrate` (`make migrate`); `admin-api` не
  применяет миграции сам и при несовпадении версии схемы отказывает в старте
  с понятной ошибкой.
- Изменение уже применённого файла миграции ломает `up` (checksum mismatch) —
  это намеренно: правки только новыми миграциями.
