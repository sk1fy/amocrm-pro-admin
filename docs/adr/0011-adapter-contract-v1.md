# ADR-0011: Контракт адаптера бекенда v1

Статус: принято, 2026-09-13.

## Контекст

Адаптер — единственный способ Admin API общаться с бекендом
([backend-adapter.md](../design/backend-adapter.md)). К этапу 4 в коде
сложились `Descriptor`, `Capabilities`, `Observation`, типизированные
ошибки и опциональные интерфейсы команд, настроек, статистики и
подписок. Нужна заморозка v1: подключение следующего бекенда не должно
требовать переделки работающих сценариев, а расширение контракта —
оставаться предсказуемым.

## Решение

1. v1 заморожен на этапе 4. Добавление опциональной возможности,
   опционального интерфейса или новых полей ответа обратно совместимо
   и остаётся v1. Переименование или удаление полей, изменение
   семантики существующих ошибок или канонических значений требует
   нового `ContractVersion` (v2). Адаптеры компилируются в сборку,
   динамической загрузки плагинов нет. `Descriptor.ContractVersion`
   объявляется адаптером и показывается в реестре; Admin API сегодня
   версии не согласовывает.
2. Возможности — единственный источник истины о доступности функций.
   Коды `Capabilities.Names()` в фиксированном порядке: accounts,
   connections, integrations, jobs, audit, diagnostics, commands,
   settings, stats, activity-deliveries, subscriptions. Вызов
   необъявленной возможности обязан вернуть `ErrUnsupported`
   (`capability_unavailable`), а интерфейс показывает unknown, а не
   ошибку. Опциональные интерфейсы (`CommandBackend`,
   `SettingsBackend`, `StatsBackend`, `SubscriptionBackend`)
   проверяются вместе с возможностью (`AsSettings`/`AsStats`/
   `AsSubscription`); read-only бекенды остаются допустимыми.
3. Локальные идентификаторы непрозрачны и адресуются в URL с
   пространством имён бекенда (`{backend}/{id}`). Единственные ключи
   связи между бекендами — amoCRM `AccountID` и `ProductCode` каталога.
   Адаптеры не видят сотрудников, роли и сессии. Admin API не пишет в
   таблицы бекендов: команды идут через собственный API/порты бекенда.
4. Состояние реестра: `catalog.Registry.Probe` читает `Health` с
   индивидуальным таймаутом (`Descriptor().Timeout`, запасной 5s) и
   кешем TTL (10s по умолчанию). Время последнего успешного
   `observed_at` и последняя ошибка переживают более поздние неудачи;
   статус — каноническая доступность источника
   (`available`/`unavailable`/`unknown`). Секретов в ответе реестра
   нет. Результаты проб питают метрики Prometheus
   ([ADR-0013](0013-admin-metrics.md)).
5. Наблюдения: у каждого результата бекенда есть `observed_at` и
   свежесть. Неизвестные значения бекенда переводятся в канон
   `unknown` + `Raw` в адаптере. Ошибки типизированы и безопасны:
   `ErrUnavailable`, `ErrTimeout`, `ErrNotFound`, `ErrUnsupported`,
   `ErrInvalidArgument`, `ErrConflict`, `ErrRejected`.

## Отклонённые варианты

- Отдельные admin-DTO на каждый бекенд: дублирование и расхождение
  канонических полей и состояний.
- Булевы возможности без опциональных интерфейсов: адаптер молча
  отвечает неверно вместо `ErrUnsupported`.
- Согласование версий через заголовки: второй версии не существует,
  переговоры не с чем вести.
- Динамическая загрузка плагинов: сложность, поверхность атаки и
  несовместимость с компилируемой сборкой.

## Последствия

Подключение бекенда = реализация интерфейсов, запись в
`deploy/backends.yaml` и тесты. Ломающие изменения требуют v2 и
параллельной поддержки двух версий. Реестр и экран Система показывают
заявленную `ContractVersion`, поэтому расхождение версий видно
оператору, но не блокирует чтение.

Форма элемента `/api/v1/system/backends` менялась с `Observation<Health>`
на `BackendRegistryEntry` в период заморозки v1 до публичного релиза;
единственный потребитель — встроенный интерфейс, поэтому изменение
принято и зафиксировано как оговорка совместимости.
