# P12.2. Компании и настройки workflow в кабинете менеджеров V1

карточку компаний внутри существующего раздела «Клиенты» и настройки
workflow внутри карточки существующего раздела «Виджеты». Рабочий frontend
находится в `frontend/manager`. Демо `frontend/src/features/managers`
не является целью. Пять существующих разделов меню сохраняются.

`aeba8e940f6b0d746ad00f898838604ae3b03cdb`.
Принятый Core в `../amocrm-pro-v1-p12-company` — `0b9db88`, полная ревизия:
`0b9db88ca94b8a8bcaba8254ca67f62e57ec4716`.
Основной checkout `../amocrm-pro` имеет `47d5270`, полная ревизия:
`47d5270d9780244d15be8e6d5810fb5c0f60a690`.
Отсутствие Platform в основном checkout не означает отсутствия принятой
Platform V1. Сверять нужно принятую ревизию, а не соседний `main`.

На `0b9db88` есть приватный read-only API Core
`api/company-crm-openapi.yaml`. Для роли `platform-company-crm` доступны
чтения Clients и WorkflowMetadata. В принятой Platform-схеме пока нет
пяти manager-операций компаний и workflow; миграции Platform заканчиваются
на `000010_manager_feed`. Это база для P12.2, а не готовая проекция.
Текущая незавершённая работа Core не служит доказательством реализации.

При сверке прочитаны Core `internal/apicontract/routes.go`,
`internal/serviceapi/contracts.go`, entrypoints `cmd/integrations` и
`cmd/activity-control`, список миграций и принятые OpenAPI. Эта плановая
часть не меняет код, контракты, миграции или design-документы.

Зафиксированное решение находится в Core worktree
`../amocrm-pro-v1-p11-release/.audit/p122-design-verdict.md`, включая
последнюю поправку об activation-qualified queue kind. Исходное исследование
находится в основном Core Git directory:
`.git/pstack/resume/ff005e5d-9d51-416d-ba15-50effbebbaf2/p122-how.md`.
Эти локальные артефакты задают план. Они не заменяют принятую реализацию,
её контракт и результаты проверок.

Владелец проекций компаний, метаданных и настроек workflow — Platform.
Admin обращается только к manager API Platform через существующий BFF.
Прямой доступ к PostgreSQL Core или Platform запрещён. Браузер не получает
credentials и не выбирает URL, host, токен или источник назначения.
Параметр `source_account_id` подтверждает уже настроенный источник.

Staff A10, эффекты CRM и intents P12.3, новые меню, GC, новые инфраструктурные
сервисы, production deployment и работа с реальными данными исключены.
`write_ready` остаётся `false`: сохранённые pipeline и stage подтверждают
членство на момент наблюдения, но не готовность создавать сделки.

## Последовательность

Каждая единица завершается проверкой и принятием точной ревизии. Следующая
единица не начинается по одному лишь наличию кода предыдущей. Создание
этого плана не означает принятия Core или разрешения пропустить его gate.

### 1. Принять владельца Core и Platform

- [ ] Зафиксировать принятую ревизию P12.2 и её фактическую OpenAPI.
  До этого не копировать схему в Admin и не начинать BFF или UI.
- [ ] Получить доказательства миграции Platform `000011`, ролей и запрета
  runtime на смену источника и изменение неизменяемых поколений.
- [ ] Подтвердить полные, частичные, пустые и устаревшие наблюдения,
  устойчивые UUID компаний, M:N контактов, неразрешённые связи,
  неоднозначность customer account ID и курсор, закрепляющий поколение.
- [ ] Подтвердить приватный TLS Core, bounded reads, общий cooldown после
  429, lease fence публикации, restart, rebind и ABA активации источника.
- [ ] Проверить поправку queue kind
  `company.refresh.<scope UUID>.<activation epoch>`. Старый worker не может
  claim работу новой активации. Новый epoch сбрасывает текущие указатели,
  старые закреплённые свидетельства остаются в истории. Это prerequisite
  владельца, а не новая логика очереди в Admin.
- [ ] Принять CAS, атомарность audit и receipt, откат reservation при
  временном 503 и точный replay после успеха при недоступном Core,
  истечении метаданных или rebind. Сверить актуальные grants и область цели.
- [ ] В Core явно включить новые suites в `scripts/platform-test.sh`.
  Успешный запуск без нужного suite не закрывает проверку.

### 2. Закрепить контракт и генерацию Admin

- [ ] Скопировать точные байты принятой Core
  `api/platform-v1-openapi.yaml` в одноимённый файл `backend/api` Admin.
  Обновить SHA-256 и attribution принятой ревизии, затем проверить совпадение.
- [ ] Расширить allowlist генерации пятью операциями ниже. Использовать
  закреплённый `oapi-codegen` 2.8.2 и проверить воспроизводимость клиента.
  Схемы DTO и операции на этом шаге только предстоит добавить.
- [ ] Добавить соответствующие браузерные схемы в
  `backend/api/openapi.yaml`, parity маршрутов и матрицу RBAC.
  Префикс владельца — `/internal/platform/v1/managers/`,
  браузера — `/api/v1/managers/`.

Все пути таблицы заданы относительно manager-префикса.

| Метод и путь | Право |
| --- | --- |
| GET `companies` | `clients.read` |
| GET `companies/{id}` | `clients.read` |
| GET `company-workflow-metadata` | `catalog.manage` |
| GET `products/{id}/company-workflow` | `catalog.manage` |
| PUT `products/{id}/company-workflow` | `catalog.manage` |

Операции в том же порядке имеют operationId `listCompanies`, `getCompany`,
`getCompanyWorkflowMetadata`, `getProductCompanyWorkflow` и
`setProductCompanyWorkflow`.

Для обоих product-маршрутов дополнительно действует принятая область
продукта. Не вводить скрытое требование `clients.read` для workflow,
его записи или получения receipt. `configuration.manage` относится к
другому ресурсу и не разрешает эту команду.

- [ ] Описать список `{items,next_cursor,source}`, отдельную карточку
  компании, metadata и workflow. Nullable data и generation до первого
  полного наблюдения не заменять пустым успешным списком.
- [ ] Проверять CRM ID как канонические положительные десятичные строки.
  Различать CompanyProjectionId, RuntimeAccountId и ProductId.
  Не приводить UUID компании к RuntimeAccountId.
- [ ] Сохранить `source_account_id`, binding revision, state, completeness,
  nullable времена наблюдения и свежести, безопасный error code и retry.
  Последняя ошибка попытки не меняет происхождение старого поколения.
- [ ] Workflow GET возвращает `configuration:null`, `version:1` до первой
  записи и не создаёт строку. Первый успешный save даёт `version:2`.
  Quoted ETag workflow независим от `Product.version` и ETag карточки.
- [ ] PUT принимает ровно `source_account_id`, `binding_revision`,
  `metadata_generation_id`, `pipeline_id`, `initial_stage_id` и существующий
  actor/command envelope. Сохранить `If-Match` и `Idempotency-Key`.
- [ ] Закрепить kind `product.company_workflow.set`, product target и
  expected workflow version. Расширение receipt и target проверять вместе
  с контрактом, не добавлять второй журнал команд.

### 3. Реализовать типизированный BFF

- [ ] Расширить существующие `managerplatform` и `platformwire`.
  Сохранить bounded context, фиксированный mTLS destination и безопасные
  ошибки. Не обращаться из BFF к Core company listener напрямую.
- [ ] Добавить явные валидаторы nullable DTO, строковых ID и enum.
  Неизвестное значение отображать как `unknown` с безопасным `raw`.
- [ ] Передавать наблюдения и `sources`, не синтезировать `available`.
  Разделить отсутствие данных, полный пустой снимок, stale и ошибку.
  Полный stale снимок допустим для чтения, но не разрешает новую запись.
- [ ] Проверять сессию, текущие grants и область продукта на сервере.
  Для PUT сохранить Origin, `X-Requested-With: admin-ui`, ключ и actor.
  При отзыве прав очистить область кеша и запретить чтение старым cursor.
- [ ] Расширить существующий intent и опрос типизированным результатом
  workflow. Сохранить проверку владельца команды и текущих прав.
  Catalog-only сотрудник получает собственный receipt без `clients.read`.
- [ ] Различать 400, безопасный 403 или предусмотренный 404, structured
  409 assertion mismatch, 422 неверного членства stage и 503 источника.
  Сохранить `Retry-After`, когда владелец его сообщает.
- [ ] При неизвестном исходе сохранять command UUID, Idempotency-Key,
  expected version и сериализованное тело без изменений. Сначала читать
  receipt, точный повтор отправляет ту же команду. Временный 503 допускает
  неизменённый повтор после восстановления по семантике владельца.
  Явный rebase после конфликта создаёт новую команду.

### 4. Добавить рабочий интерфейс

- [ ] В существующем WidgetsPage и ProductEditor добавить workflow section.

- [ ] Показать отсутствие конфигурации, metadata, полноту и время источника,

- [ ] Выбор pipeline сбрасывает stage. Сохранение доступно только с полными

- [ ] Перед новыми полями обновить `design/data-sources.md`, перед

## Приёмка

Часть принимается после последовательного закрытия всех единиц выше.
Пять операций соответствуют принятой схеме владельца, а существующие
маршруты аккаунтов и пять меню сохраняют поведение. Компании не требуют
искусственного runtime UUID. Новый workflow сохраняется только на свежих
метаданных, имеет собственный ETag и безопасно восстанавливается после
потери ответа без изменения идентичности команды.

До приёмки Core, реальной цепочки, полного `make check` Admin и независимого
review P12.2 Admin остаётся открытым. Следующая часть P12.3 не начинается
на основании этого документа.
