# A07. Сотрудники и менеджерский доступ

## Объём

Admin реализует локальные HTTP-контракты, identity, приглашения,
квитанции, пагинацию и журнал безопасности. Core публичный API и
worker не меняются. Техническое отключение в Admin HTTP, CLI и Store
использует общий порядок блокировок с менеджерскими изменениями.

## Владение и данные

Admin начинает с принятой A06 `f597270`. Сотрудниками, приглашениями,
сессиями, grants и аудитом владеет Admin. Platform в этом сценарии
может быть недоступна.

Непустой набор manager grants разрешает менеджерский вход при активной
identity и установленном пароле. Отзыв очищает набор grants. Восстановление
явно задаёт новый набор. Дополнительного флага manager_enabled нет.
Администратор имеет активную identity, пароль и `staff.manage`, как в A01.

Новый `employees.technical_access` равен true для существующих записей.
Приглашение создаёт passwordless identity с false. Core login, чтение
Core-сессии и свежая RBAC-проверка требуют true. Менеджерские действия
не меняют техническую роль или глобальный employee status.

Staff DTO содержит id, email, name, производный status, grants,
version из manager_grants_version, changed_at и nullable changed_by.
Приглашение хранит только хеш токена, срок, автора, consumed/revoked.
Безопасная квитанция команды хранит actor, ключ, хеш нормализованного
запроса с маршрутом и ожидаемой версией, результат и дату.

## HTTP

Все маршруты начинаются с `/api/v1/managers`.

| Метод и suffix | Права | Результат |
| --- | --- | --- |
| GET /staff | staff.manage | Список, limit 25/100, поиск, cursor |
| GET /staff/grants | staff.manage | Канонический каталог grants |
| GET /staff/{id} | staff.manage | Staff DTO и ETag |
| POST /staff | staff.manage + identity.manage | Новая identity и приглашение |
| PATCH /staff/{id} | staff.manage | Полная замена grants, If-Match |
| POST /staff/{id}/invitation/reissue | staff.manage + identity.manage | Перевыпуск ожидающего приглашения, If-Match |
| POST /staff/{id}/sessions/revoke | staff.manage + identity.manage | Отзыв managers-сессий |
| POST /auth/invitations/accept | Валидный invitation token | Установка пароля и потребление токена |
| GET /security/audit | security.audit.read | Только разрешённые менеджерские события |

Привилегированные записи используют CSRF и Idempotency-Key. PATCH принимает
`grants`. POST /staff принимает `email`, `name`, `grants`. Неизвестные grants,
поля, дубликаты и некорректные версии отклоняются. Собственное добавление
grants запрещено. Пустой набор означает отзыв менеджерского доступа.

Существующий email возвращает 409. Приглашение не меняет пароль или grants
существующей identity. Выдать ей менеджерские права можно через PATCH.
Токен принимается только для исходной manager-only passwordless identity.
Новая команда повторного принятия и истёкшее, отозванное или заменённое
приглашение отвергаются. При потере ответа точный повтор принятия с теми
же токеном, UUID команды и паролем возвращает `accepted=true` без эффекта.
Пароль сверяется с исходным Argon2-хешем; быстрый хеш не сохраняется.

Ссылка показывается один раз в первом успешном ответе, передаёт токен
в URL-фрагменте и использует Cache-Control no-store. Оператор копирует
её самостоятельно. Доставка сообщений в объём A07 не входит.
Квитанция никогда не хранит ссылку или токен. Точный повтор возвращает
тот же безопасный результат с явным link_unavailable. После потери ответа
оператор обновляет список и явно перевыпускает приглашение новой командой.
Перевыпуск отзывает прежний токен. Принятую identity перевыпуск не сбрасывает.

Списочные cursor подписаны HMAC с domain separation от внутреннего
хеша токена текущей manager-сессии. Они связывают actor/session, версию
прав, фильтры, сортировку, срок и позицию. Новая сессия начинает список заново.
Хеш сессии не передаётся браузеру или в DTO.

## Атомарность

employees.Access остаётся владельцем транзакции. Все изменения, влияющие
на существование менеджерского администратора, сначала берут существующий
LOCK TABLE manager_grants IN SHARE ROW EXCLUSIVE MODE. Bootstrap, manager
PATCH и отключение через технические HTTP, CLI и Store используют один
порядок блокировок. CLI переходит на Access.Update с атомарным аудитом
и отзывом сессий.

Под блокировкой повторно проверяются текущая сессия и grants инициатора.
Затем проверяется квитанция, блокируется target, сверяется ожидаемая версия,
применяется изменение и проверяется сохранение администратора. Эффект,
версия, отзыв соответствующих сессий, аудит и безопасная квитанция
фиксируются вместе. Квитанция проверяется раньше устаревшей target-версии,
но после текущего права инициатора.

Менеджерский отзыв использует явный managers audience. Существующий
RevokeAllTx для глобального employee disable сохраняет широкую область.
Техническая смена роли сохраняет менеджерские сессии.

Принятие и перевыпуск приглашения сериализуются теми же блокировками.
Проверка последнего администратора учитывает только активных сотрудников
с паролем. Ожидающее приглашение не заменяет администратора.

Down-миграция отклоняется при manager-only identities или сохраняемых
приглашениях/квитанциях. Удаление technical_access позволило бы старому
бинарю открыть технический доступ такой identity.

## Приёмка

- Два конкурирующих изменения сохраняют одного администратора.
- Гонка manager PATCH с техническими HTTP и настоящим CLI disable проверена в PostgreSQL.
- Устаревший ожидающий инициатор и собственная эскалация отклонены.
- Отказ записи аудита или квитанции откатывает весь эффект.
- Приглашение принимается один раз, повтор команды и явный перевыпуск безопасны.
- Менеджерский отзыв действует следующим запросом, техническая сессия сохраняется.
- Приглашённый сотрудник не входит в Core Admin.
- Cursor и аудит сохраняют область доступа и исключают секреты.
- Пятый раздел работает в браузере при отключённой Platform.

## Отчёт

Результаты работающего контура добавляются после приёмки A07.
