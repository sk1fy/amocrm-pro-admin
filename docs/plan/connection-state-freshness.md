# Patch-план: актуальность состояния подключений

Статус: completed (инженерная часть; rollout отдельно)
Дата: 2026-09-14  
Репозитории: `amocrm-pro-admin`, `amocrm-pro`

## Объём

Сверено 2026-09-19 с текущим кодом двух репозиториев. Реализация:

- Patch 1: общая политика Query для видимых backend-экранов,
  refetch при возврате, обновление после терминальных команд, время снимка.
- Patch 3: безопасный Core snapshot подтверждённой проверки, fencing
  по версии credentials и состоянию установки, keyset verification filter;
  совместимый адаптер старого Core.
- Patch 2: отдельные факты установки, локальной авторизации и проверки;
  verification в списках, агрегатах и обзоре.
- Patch 4: scheduler в Worker, durable commands, общий PostgreSQL admission,
  rollout flag по умолчанию выключен, лимиты, jitter/backoff/Retry-After.
- Локальные тесты, метрики, Grafana/Prometheus артефакты и runbook.

Единый срок свежести: 90 минут, возвращается Core в snapshot. Это согласовано
с интервалом scheduler 1 час ±20% (48–72 минуты); frontend не вычисляет freshness.
Проекция проверки хранится владельцем Core отдельно от OAuth credentials;
результат появляется только вместе с подтверждённой command-квитанцией.
Новая версия OAuth делает прежнее наблюдение неизвестным при чтении.
Production rollout и наблюдение 24 часа выполняет оператор отдельно.

## Проблема

Текущий бейдж подключения отражает прежде всего сохранённое значение
`installations.status` из Core. Это состояние меняется после OAuth, операторской
команды или достоверной ошибки авторизации во время обращения к amoCRM, но само
по себе не является периодической проверкой доступности amoCRM.

Admin UI получает актуальный снимок Core при HTTP-запросе, однако списки
аккаунтов, обзор и карточка подключения не опрашиваются автоматически.
`staleTime=10s` ограничивает свежесть клиентского кеша, но не запускает polling;
`refetchOnWindowFocus` отключён. Поэтому уже открытый экран может показывать
старое состояние до навигации, ручного повтора, завершения команды или reload.

Отдельная команда `check` выполняет реальный запрос к amoCRM и сохраняет
`authorization_check`, но эта проверка запускается вручную и через 15 минут
лишь помечается `stale` — автоматически она не повторяется.

## Цель

Сделать состояние подключения понятным и предсказуемо актуальным, не смешивая:

1. жизненный цикл установки в Core;
2. вычисленное состояние локальных OAuth credentials;
3. результат последней живой проверки amoCRM;
4. доступность самого backend Core;
5. проблемы webhook и фоновых задач.

Система не должна показывать `active` как подтверждённое онлайн-соединение,
если живой проверки не было или она устарела.

## Инварианты безопасности

- Только достоверные `401` или `invalid_grant` могут переводить установку в
  `reauth_required`.
- Timeout, DNS, `429` и `5xx` отражаются как недоступная/ограниченная проверка,
  но не отзывают рабочую авторизацию.
- Фоновая проверка не должна раскрывать access/refresh token, ответ `/account`
  или персональные данные в логах, метриках и operation receipts.
- Проверки ограничиваются по backend, интеграции и аккаунту; обязательны jitter,
  backoff и глобальный лимит параллелизма.
- `disabled` и `uninstalled` не проверяются и не могут быть возвращены в
  `active` фоновой задачей.
- Поздний ответ проверки не может перезаписать результат новой OAuth-ротации;
  применяется fencing по `token_version`.

## Целевая модель отображения

### Состояние установки

Источник: `installations.status`.

Значения сохраняются без изменения контракта:
`pending`, `authorizing`, `active`, `reauth_required`, `disabled`,
`uninstalled`, `error`.

В UI блок называется **«Состояние установки»**, а не просто
«Состояние подключения».

### Локальная авторизация

Источник: наличие credentials, `expires_at`, refresh lease, `token_version` и
статус установки.

Значения: `missing`, `refreshing`, `expired_refreshable`, `valid`,
`reauth_required`. Это вычисленный локальный факт; он не означает, что amoCRM
принял токен.

### Проверка amoCRM

Источник: последняя завершённая операция `check`.

Классификация:

| Значение | Смысл |
| --- | --- |
| `verified_ok` | `/account` успешно ответил |
| `auth_error` | amoCRM достоверно отклонил авторизацию |
| `network_error` | проверка не дошла до ответа amoCRM |
| `rate_limited` | получен `429`, учитывается `Retry-After` |
| `internal_error` | проверка не завершилась из-за внутренней ошибки |
| `unknown` | проверка ещё не выполнялась |

Каждый результат показывает `observed_at` и freshness:

- `fresh`: не старше 90 минут;
- `stale`: старше 90 минут;
- `unknown`: результата нет;
- `unavailable`: текущая попытка не смогла получить достоверный результат.

Порог 90 минут — единая конфигурационная константа Core. Он согласован
с часовым целевым интервалом и jitter ±20%; UI получает срок из API.
Fallback старого Core сохраняет прежние 15 минут.

### Итоговый индикатор аккаунта

Агрегат не заменяет отдельные факты и рассчитывается в следующем приоритете:

1. backend недоступен и нет полного снимка → `partial`;
2. `reauth_required` или `auth_error` → `needs_action`;
3. отсутствуют credentials у `active`/`pending` → `needs_action`;
4. ошибка установки или webhook → `error`;
5. pending/authorizing, failed jobs или временно неуспешная проверка →
   `attention`;
6. все установки disabled/uninstalled → `inactive`;
7. установка active, локальная авторизация допустима и свежая проверка успешна
   → `ok_verified`;
8. установка active, но проверка unknown/stale → `ok_unverified`.

Если добавление `ok_verified`/`ok_unverified` ломает публичный v1-контракт,
оставить канонический `ok`, но обязательно выводить рядом отдельный бейдж
проверки. Не кодировать verification в `installations.status`.

## Patch 1 — автоматическое обновление Admin UI

Репозиторий: `amocrm-pro-admin`.

1. Включить `refetchOnWindowFocus` для backend-данных, не меняя поведение
   сессий и статических справочников.
2. Добавить polling только для видимой вкладки:
   - обзор и реестр backend: 15 секунд;
   - список аккаунтов: 90 секунд;
   - карточка аккаунта и подключения: 15 секунд;
   - страницы с активной операцией/задачей сохраняют текущие 1,5 секунды до
     терминального состояния, затем переходят на обычный интервал.
3. Останавливать polling при скрытой вкладке или потере фокуса окна и
   возобновлять с немедленным refetch при возврате.
4. Не запускать параллельный запрос, пока предыдущий не завершён.
5. Добавить кнопку «Обновить» и текст «Обновлено …» на обзор, список аккаунтов и
   карточку подключения.
6. После терминальной Admin-команды инвалидировать `accounts`, `account`,
   `connection`, `stats`, `backends` и выполнить немедленный refetch видимых
   запросов.
7. Сохранять предыдущие данные во время refetch, но показывать индикатор
   «Обновляется…»; ошибка нового запроса не должна выглядеть как подтверждение
   прежнего состояния.

### Тесты Patch 1

- Vitest с fake timers: запрос повторяется через заданный интервал.
- Polling останавливается в скрытой вкладке и возобновляется при visibility.
- Возврат фокуса вызывает refetch backend-данных.
- Терминальная команда инвалидирует все связанные query keys.
- Старый ответ не перезаписывает данные после смены сотрудника/сессии.
- Playwright: состояние изменяется в fixture backend и появляется без reload не
  позднее чем через 90 секунд.

## Patch 2 — честная семантика и freshness в интерфейсе

Репозиторий: `amocrm-pro-admin`.

1. Переименовать общий бейдж в «Состояние установки».
2. Всегда показывать отдельные блоки:
   - локальная авторизация;
   - последняя проверка amoCRM;

   - источник и `observed_at`.
3. Для `unverified`, `unknown` и `stale` запрещены зелёные тексты
   «подключение проверено» и «всё работает».
4. В списке аккаунтов добавить компактный verification-бейдж и tooltip с
   временем последней проверки.
5. На обзоре разделить счётчики:
   - нужна повторная авторизация;
   - проверка устарела/не выполнялась;
   - временная ошибка проверки;
   - backend недоступен.
6. Не считать отсутствие результата проверки нулём или успехом.

### Тесты Patch 2

- Табличные component tests для всех комбинаций installation/auth/check.
- `active + stale check` отображается как «активно, проверка устарела».
- `active + network_error` не отображается как reauth.
- `active + auth_error` требует действия.
- `source unavailable` не подменяется состоянием сохранённой строки.
- Проверяется доступность: текстовые подписи не зависят только от цвета.

## Patch 4 — фоновая контролируемая проверка

Репозиторий: `amocrm-pro`.

Выполнять после Patch 1–3 и отдельно включать feature flag.

1. Добавить планировщик, который ставит idempotent check-команды для
   `active`-установок с отсутствующей или устаревшей проверкой.
2. Начальные безопасные параметры:
   - целевой интервал: 1 час;
   - jitter: ±20%;
   - не более 2 одновременных запросов на интеграцию;
   - глобальный лимит настраивается env;
   - exponential backoff для network/5xx;
   - `Retry-After` обязателен для `429`.
3. Не проверять disabled/uninstalled и установки с активным refresh lease.
4. Использовать существующий command/receipt механизм и стабильный
   idempotency key на временное окно.
5. Перед сохранением результата сверять `installation_id`, status и
   `token_version`; устаревший результат сохранять только в аудит как
   superseded.
6. Не переводить установку в `error` из-за временной недоступности.
7. Добавить feature flag и параметры rollout: сначала один account/integration,
   затем ограниченный процент, затем все активные установки.

### Тесты Patch 4

- Один check на установку в пределах окна при нескольких репликах scheduler.
- Jitter/backoff и `Retry-After` через fake clock.
- 401/invalid_grant атомарно переводит актуальную версию в reauth.
- Timeout/429/5xx не меняют installation status.
- Поздняя проверка старого `token_version` не портит новую OAuth-сессию.
- Disabled/uninstalled не проверяются.
- Перезапуск worker не создаёт шторм команд.

## Наблюдаемость

Добавить метрики с конечными label-наборами:

- `admin_connection_checks_total{classification}`;
- `admin_connection_check_duration_seconds`;
- `admin_connection_checks_inflight`;
- `admin_connection_verification_age_seconds`;
- `admin_connection_verification_stale_total`;
- `admin_connection_check_scheduler_lag_seconds`.

Не использовать account/installation ID, домен или email как metric label.

Grafana должна показывать:

- долю active-установок со свежей успешной проверкой;
- количество unknown/stale;
- auth errors отдельно от network/429/5xx;
- возраст самой старой проверки;
- scheduler lag и backlog.

Alertmanager:

- warning при росте доли stale/unknown выше порога в течение 15 минут;
- warning при scheduler lag;
- critical только при системной недоступности проверок, не по единичному
  клиентскому `auth_error`.

## Rollout

1. Выпустить Patch 1 без изменения Core.
2. Выпустить Core-часть Patch 3, затем совместимую Admin-часть.
3. Выпустить Patch 2 после появления verification summary в списках.
4. Включить Patch 4 только для тестовой интеграции.
5. Наблюдать rate limit, latency и число ложных auth errors не менее 24 часов.
6. Расширять охват ступенями 5% → 25% → 100%.
7. При проблемах отключить scheduler feature flag; UI polling и ручной check
   продолжают работать.

## Критерии приёмки

- Изменение fixture-состояния видно в открытом списке не позднее 90 секунд без
  reload.
- Изменение реального состояния после завершённой Admin-команды видно не позднее
  3 секунд.
- Пользователь всегда видит время последнего backend-снимка и живой проверки.
- `active` без свежей проверки не называется подтверждённым подключением.
- 401 приводит к `reauth_required`; timeout/429/5xx — нет.
- При недоступном Core UI показывает partial/unavailable и возраст последнего
  успешного снимка, а не старый зелёный статус без предупреждения.
- После OAuth старый check-result не может ухудшить новую установку.
- Все новые интервалы конфигурируемы и покрыты тестами с fake clock.
- CI обоих репозиториев и server smoke/e2e проходят.

## Вне объёма

- Проверка прав пользователя amoCRM при каждом открытии Admin UI.
- Хранение ответа `/account` целиком.
- Автоматическая повторная OAuth-авторизация.
- Перевод в reauth по косвенным сигналам webhook, lag или отсутствию событий.
- Использование активности сотрудников как признака исправности OAuth.
