# A05. Рабочий раздел «Виджеты»

## Объём

База Admin для контракта A05 — `a410e75`. Владелец продуктов — Platform P08
`88ed4d8` в `amocrm-pro`. Семантику задаёт его runbook
`docs/runbooks/platform-catalog-v1.md`. SHA-256 P01 совпадает с закреплённым
`78f2ce5efd5e842cf5fcf2f431a6a1376439bbba8561c9ca72ed1cb0a917dbf7`.

Браузерный контракт добавляет ровно пять операций `/api/v1/managers`:

| Метод и путь | Право |
| --- | --- |
| GET `/products` | `clients.read` |
| POST `/products` | `catalog.manage` |
| GET `/products/{id}` | `clients.read` |
| PATCH `/products/{id}` | `catalog.manage` |
| GET `/products/{id}/metrics` | `stats.read` |

Список передаёт `limit`, `cursor`, `q`, `line`, `availability` владельцу.
Метрики передают `from`, `to` и доступны с отдельным `stats.read`.
Создание возвращает `201`, обновление — `200`. ETag содержит версию
карточки `Product.version`. Выбранная версия тарифа отображается отдельным
полем `tariff_version`. PATCH использует `If-Match`. Повтор без изменения
возвращает текущую версию карточки.

POST принимает существующий технический продукт по коду и сохраняет его
UUID. Новый код создаёт продукт. UUID результата сверяется с `Product.code`
исходной команды.
Менеджер сохраняет полный подтверждённый набор `integration_refs`.
Справочник тарифов API не предоставляет. `tariff_version` выбирает только
подтверждённую владельцем версию или `null` для снятия выбора.

`trial_policy` сохраняет форму P01. FREE использует `free` с `null`,
отключение — `none` с `null`, TOP — `once` с 90 днями,
PRO — `once` с 7 или 14 днями. Владелец проверяет подтверждённое правило.

Команды используют UUID `Idempotency-Key`, `Origin` и `X-Requested-With`.
Неизвестный исход возвращает `202` с `ManagerOperation`, `Location` и
`Retry-After`. Опрос требует владельца intent и актуальную область цели.
Для команд каталога достаточно `catalog.manage`. Старые команды
сохраняют прежние проверки `clients.read` и права вида команды.

`confirmed_installations` считает подтверждённые эпизоды установки.
`to` включается как календарный день в часовом поясе владельца.
`active_accesses` показывает текущие доступы независимо от диапазона.
`activations` показывает число допущенных подтверждённых фактов. До открытия
G03 метрика равна нулю с отметкой об отсутствии покрытия источником.

Контракт, генерируемый клиент, BFF и интерфейс используют эти пять операций.
Фильтры и выбранный продукт сохраняются в URL. Смена прав обновляет область
запросов и черновиков. Конфликт версии сохраняет введённые поля до явного
применения к актуальной версии. Повтор неопределённого исхода использует
исходные тело, ключ и версию команды.

## Приёмка

- Пять операций и права браузера совпадают с P01, старые 19 операций A04
  сохраняют контракт.
- Формы Product, TrialPolicy, ProductMetrics, списков и тел команд
  совпадают с P01, включая обязательные поля, `null` и запрет лишних полей.
- Генерация включает 29 операций и воспроизводит `client.gen.go`.
- Хеш P01 совпадает с закреплённым контрактом.
- Реализация A05 подтверждает сохранение после перезагрузки, конфликт
  версий, точный повтор и сверку после потери ответа.
- Метрики доступны сотруднику только со `stats.read`, запись и её опрос
  доступны сотруднику только с `catalog.manage` без `clients.read`.
- UI различает отказ источника, отсутствие G03 и реальные нулевые счётчики.

## Отчёт

Код `6121c8b` прошёл сквозную проверку с Core, двумя процессами Platform,
Admin, тремя PostgreSQL 17 и Chromium. Два сотрудника сохранили карточку,
получили 409 для старой версии и применили сохранённый черновик к свежим
полям. После перезапуска Admin и Platform сохранились название, выбранный
тариф и правило теста. Записи ранее выданных сроков совпали до и после
редактирования каталога.

HTTP-проверка подтвердила отдельные права чтения, записи и метрик,
восстановление потерянного ответа с тем же ключом, receipt собственного
сотрудника, отклонение чужого опроса, CSRF, повтор без изменения версии и
причины бизнес-отказа. Регрессии BFF и миграций прошли на обычном
PostgreSQL 17 с включённым fsync. Сохранены исходные правила опроса A04.

Независимое ревью выявило выбор устаревших привязок при одинаковой версии
карточки. Исправление выбирает свежий ответ владельца. Регрессия проверяет
показ нового набора связей, следующий PATCH и исходное тело уже ожидающей
команды. Генерация UUID использует существующий `createRequestKey`.
Два теста воспроизвели ошибку при отсутствии `crypto.randomUUID`, затем
проверили UUIDv4, создание и проверку установки, точный повтор. Все 34
теста менеджерской зоны и генератора ключей, frontend lint и сборка прошли.

Итоговый прогон `/tmp/rakurs-v1-a05-live.kenbhtgn/run.sh` прошёл с
Chromium до и после перезапуска. Перед рестартом выполнены три сценария,
после — сценарий чтения сохранённых данных. Пропуски выбирают сценарий
соответствующей фазы. HTTP-проверка сохранена в
`/tmp/rakurs-v1-a05-http-final.log`, браузерная — в
`/tmp/rakurs-v1-a05-browser-final.log`, обычный PostgreSQL с race — в
`/tmp/rakurs-v1-a05-boundary-final.log`.

Полные общие проверки Admin и нагрузочные регрессии Platform выполняются
на этапах выпуска P11, A08 и A09. Их прежние результаты и исправления
зафиксированы в HTML-роадмапе.
