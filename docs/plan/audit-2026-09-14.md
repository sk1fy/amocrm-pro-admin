## Исправления по результатам аудита

Приоритеты P1/P2 ниже — порядок устранения в проекте, не оценка CVSS.

### A1 — P2: Admin принимал только первый JSON-префикс

`backend/internal/httpapi/router.go`, `decodeJSON`: один `Decode` поверх
`io.LimitReader` не проверял конец тела. `{} {}`, `{} garbage`, `null`
и объект с хвостом пробелов за лимитом могли не отвергаться декодером.
Это нарушение контракта запроса, не доказательство обхода авторизации.

Добавлен `internal/platform/jsonbody.DecodeObject`: чтение не более
`limit+1`, проверка фактического лимита, верхнего уровня object,
неизвестных полей и EOF после единственного значения. Сохраняются
безопасный error envelope и закрытие HTTP body. Регрессии проверяют
границу размера, хвосты, тип верхнего значения и ошибки чтения.

### A2 — P1: Core округлял числа при расчёте request_hash

В `internal/admincommand/types.go` канонизация через `any`/`float64`
сводила `9007199254740992` и `9007199254740993` к одному значению.
Прикладная структура при этом сохраняла исходный `int64`. Другой payload
с тем же ключом мог выглядеть как повтор прежней команды.

В [Core PR #56](https://github.com/sk1fy/amocrm-pro/pull/56) применён
`Decoder.UseNumber()`, проверены ошибки сериализации и добавлены тесты
границ 2^53/MaxInt64, порядка полей и общей идентичности между сотрудниками.

### A3 — P2: Admin не нормализовал вложенные объекты

В `backend/internal/operations/service.go` сериализация
`map[string]json.RawMessage` сортировала лишь верхний уровень. Изменение
порядка свойств `display_window` меняло хеш семантически той же команды.

Теперь перед admission вызывается `jsonbody.CanonicalObject`: сортируются
вложенные объекты, сохраняются порядок массивов и числовые токены.
Добавлены изолированные unit-тесты и PostgreSQL integration-сценарий
проверки того же operation ID, единственного dispatch и конфликта для
другого большого целого. Последний сценарий добавлен, но не запускался.
Это не заявляется как реализация RFC 8785.

### A4 — P2: неполный перечень изменённых полей в аудите

`changedFields` учитывал интеграции, но не большую часть настроек Activity,
панелей и lead-status. Дополнен разрешённый список имён полей и добавлена
регрессия. Значения payload, имя панели, список сотрудников и секреты
в metadata не добавляются: сохраняются только названия полей.

### A5 — P1: restore-check мог удалить существующую БД

`deploy/scripts/restore-check.sh` выполнял предварительный
`DROP DATABASE ... WITH (FORCE)` для задаваемого `SCRATCH_DB`. Сравнение
с `POSTGRES_DB` не защищало другие уже существующие БД экземпляра.
Также не ограничивалась длина SQL-идентификатора.

Предварительный DROP удалён. Только успешный CREATE даёт текущему запуску
право cleanup. Запрещены системные имена, имя live DB и идентификаторы
длиннее 63 ASCII-символов. Сигналы завершают выполнение с cleanup,
а не продолжают проверку после удаления scratch. Из stdout убран email
сотрудника. Защита проверена на подставных командах, не на production.

### A6 — P2: права и коллизии резервных копий

`deploy/scripts/backup.sh` наследовал umask вызывающей оболочки и
использовал имя с точностью до секунды. Возможны доступ к dump другим
пользователям хоста и перезапись одновременных копий.

Добавлены `umask 077` и уникальный временный файл через `mktemp`.
Проверены права `0600`, два запуска с одним timestamp и удаление
незавершённого файла при ошибке `pg_dump`. Права ранее созданных копий
не меняются; шифрование и внешнее хранение остаются обязанностью оператора.

### A7 — P2: неполный обязательный набор проверок

Исходный `make check` не включал `e2e`, хотя style guide требовал
сквозную проверку перед слиянием. Добавлены `e2e` и `scripts-test`.
Предлагаемый GitHub Actions workflow запускает те же группы проверок
раздельно: документация/скрипты, lint, unit, PostgreSQL integration, E2E.
Это конфигурация CI, а не доказательство успешного прогона.

## Совместимость исправлений

Маршруты, права ролей, схема БД и публичный Core API не расширяются.
Поведение неправильных JSON-тел становится строже: HTTP 400 вместо
обработки допустимого префикса. Существующие request_hash не мигрируются,
поскольку исходные секретные payload намеренно не хранятся.

После обновления повтор исторической команды с ранее неканоническим
вложенным объектом либо округлённым числом может получить конфликт.
Сначала проверить operation/receipt и фактический объект. Не обходить
конфликт автоматическим новым ключом и не повторять внешнюю мутацию
вслепую. Восстановление уже принятых операций чтением квитанции сохраняется.

## Открытые риски и остаток работ

**R1 — P1, Core/Activity:** `Store.Execute` держит транзакцию квитанции
и savepoint при вызовах `applyActivity`. Commit внешнего владельца не
откатывается вместе с Core. Нужны durable intent до dispatch, единый
command ID у владельца, чтение исхода после потери ответа и fault-injection
между внешним эффектом и commit квитанции. Для patch панели отдельно
проверить командную идемпотентность, не только CAS. Перенос за commit
без такой схемы не является исправлением. Этот блок здесь не реализован.

**R2 — требуется проверка атомарности:** `applyLeadStatus` вызывает
`ConfigureAdmin` без передачи текущего `domainTx`. Нужно проследить
транзакцию RuleStore и проверить rollback/повтор после сбоя commit.
Это выявленный риск на границе вызова, не воспроизведённый сбой БД.

**R3 — приёмка выпуска:** Docker-прогоны обоих репозиториев, роль/отзыв
доступа в браузере, реальный OAuth, пилот с сотрудниками, нагрузка
10^4–10^5 и EXPLAIN на пилотном Core не выполнены в этой среде.
Нужны сохранённые результаты для проверяемых commit SHA.

**R4 — эксплуатация restore:** существующий сценарий сравнивает dump
с текущими live row counts. Для воспроизводимой проверки нужен
согласованный свежий backup при остановленных изменениях либо отдельный
manifest снимка. Изменения живой БД после backup могут дать ложное
несовпадение; автоматический snapshot manifest здесь не добавлен.

**R5 — окружение и доступ:** на снимке Admin main не защищён от прямого
push. После успешного CI следует включить required checks и PR-review
в настройках GitHub. Настройки защиты, production credentials,
TLS/reverse proxy и права реального PostgreSQL этим изменением не менялись.

## Фактически выполненные проверки

В изолированной среде Go 1.23.2, без загрузки полного модуля:

- `jsonbody`: `go test -race -count=1 -v` — пройдено; 34 табличных
  случая плюс отдельные проверки ошибки reader и ограничения чтения.
- `make scripts-test` — 11 проверок с command doubles пройдено.
  Тот же safety-test на исходных скриптах завершается ошибкой, как ожидается.
- `sh -n` для изменённых shell-скриптов — пройдено.
- `make -n check` — проверен состав команд, включая Playwright и скрипты;
  это dry run, не выполнение Docker-команд.
- Потеря точности Core воспроизведена отдельно на стандартной библиотеке.

Полные `make check`, проектные Go-тесты, Vitest, Playwright, миграции
и настоящий `pg_restore` локально не запускались: Docker отсутствует,
сетевое клонирование недоступно. Чтение и запись кода выполнены через
GitHub connector. Версия standalone Go не заменяет проектную Go 1.25.
Исторические результаты в планах не засчитывались как новый прогон.

## Критерий закрытия

Предлагаемые PR должны пройти review и весь набор проверок на своих
head SHA. Для закрытия этапа 4 отдельно нужны протокол пилота и
эксплуатационные evidence. R1/R2 должны иметь проверенное решение либо
явно согласованное ограничение выпуска; данный отчёт не закрывает их
автоматически. Слияние и развёртывание в рамках аудита не выполнялись.
