### A1–A4: контракты JSON, идемпотентность и аудит

В `backend/internal/httpapi/router.go` прежний единственный Decode поверх
LimitReader не отвергал `{} {}`, `{} garbage`, `null` и хвост за лимитом.
Новый `internal/platform/jsonbody.DecodeObject` сохраняет закрытие HTTP
body и безопасный error envelope. Это исправление контракта запроса,
не заявление о найденном обходе авторизации.

В Core `normalize` числа `9007199254740992` и `9007199254740993` имели
одинаковое промежуточное значение float64, хотя доменная структура
получала разные int64. Теперь числовые токены сохраняются. В Admin
`CanonicalObject` также сортирует вложенные свойства `display_window`.
Реализация не объявляется RFC 8785 canonical JSON.

Регрессии проверяют same operation ID, один dispatch при перестановке
вложенных полей и конфликт при другом большом целом. Имена изменённых
полей добавлены в `changedFields`; секреты, имя панели и employee IDs
в значения audit metadata не добавляются.

### A5–A6: безопасная проверка резервного копирования

Прежний restore-check выполнял `DROP DATABASE ... WITH (FORCE)` до
CREATE, а проверка равенства POSTGRES_DB не защищала другие БД экземпляра.
Теперь уже существующая scratch DB приводит к отказу без DROP/restore.
Имена ограничены 63 ASCII-символами; system/live имена запрещены.
Сигналы завершают сценарий с cleanup, не продолжают его после удаления
scratch. Email сотрудника убран из stdout.

Backup создаёт файлы с правами 0600 и уникальными именами даже при одном
timestamp. Старые backup-файлы не меняются. Шифрование, внешнее хранение
и контроль доступа к каталогам остаются обязанностью оператора.
11 сценариев command doubles проверяют эти свойства, но не заменяют
настоящий pg_restore.

не снятие или ослабление прежних проверок.

## Совместимость

Новых маршрутов, ролей или миграций нет. Неправильные JSON-тела получают
400 вместо обработки допустимого префикса. Прежние request_hash не
переписываются: исходные секретные payload намеренно не хранятся.

Исторический повтор с ранее неканоническим вложенным объектом или
округлённым числом может получить конфликт после обновления. Сначала
проверить operation/receipt и фактический объект. Не обходить конфликт
автоматической повторной мутацией с новым ключом. Восстановление ранее
принятых операций чтением квитанции сохраняется.

## Незакрытые ограничения и критерий выпуска

**R1 — P1, Core/Activity:** внешние `AdminConfigure`, `AdminCreatePanel`,
`AdminPatchPanel`, `AdminRotateShare` остаются внутри транзакции квитанции
Core. Откат SQL не откатывает внешний эффект. Требуются durable intent
до dispatch, единый command ID владельца, чтение исхода при потере ответа
и fault-injection между эффектом и commit. Для patch нужна командная
идемпотентность, не только CAS. Исправление SQL lead-status не закрывает
этот распределённый путь. Перенос внешних вызовов здесь не реализован.

**R2 — lead-status:** первоначально отмеченная неопределённость атомарности
устранена в коде A10. Закрытие проверки привязано к успешному выполнению
новой PostgreSQL-регрессии на Core 8357555 или последующем head.

**R3 — production-приёмка:** реальный OAuth, нагрузка 10^4–10^5 установок,
EXPLAIN тяжёлых Core-запросов, настоящий restore и пилот сотрудников не
выполнялись. Fixture E2E не подменяет интеграцию с настоящим amoCRM.

**R4 — restore snapshot:** сравнение backup с текущими live row counts
может дать ложное несовпадение после изменений живой БД. Нужен
согласованный backup при остановленных изменениях либо manifest снимка.
Такой manifest здесь не добавлен.

**R5 — эксплуатационный доступ:** защита main/required checks, TLS,
reverse proxy, реальные credentials и PostgreSQL-роли не менялись.

Для выпуска нужны review обоих PR, зелёные проверки их head,
протокол эксплуатационной приёмки и проверенное решение R1 либо явно
согласованное ограничение выпуска. План не помечается выполненным на 100%.
