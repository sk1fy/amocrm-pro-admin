# Проверка лимита пользователей подписки

## Объём

Platform 000028 приостанавливает TOP и Единую подписку после первого
превышения по последнему наблюдению. Сохраняем данные предыдущего
успешного наблюдения и определяем состояние по двум последовательным
наблюдениям для действующего лимита. Менеджерский API передаёт
предупреждение в карточку клиента.

Учитываются плановые и запрошенные менеджером обновления пользователей.
Оба способа используют одну очередь обновления. Наблюдение для подготовки
сделки обновляет данные карточки отдельно от проверки лимита.

## Приёмка

- Первое свежее успешное наблюдение выше лимита показывает предупреждение,
  пакет продолжает действовать. Второе подряд приостанавливает пакет.
- Успешное наблюдение в пределах лимита восстанавливает пакет и начинает
  отсчёт заново. Ошибка, повтор того же наблюдения и запоздалые данные
  не меняют последовательность. Собственные сроки виджетов сохраняются.
- Выдача и изменение лимита начинают отсчёт со следующего наблюдения.
  Продление действующего пакета с прежним лимитом сохраняет отсчёт.
  Старое превышение после миграции считается одним наблюдением.
- После изменения лимита учитываются только проверки, принятые Platform
  после изменения. Опережение или отставание часов Core сохраняет этот
  порядок.

## Отчёт

Дата: 2026-11-26. База amocrm-pro-admin `74a7ee1`, amocrm-pro `375b723`.

### Реализованные экраны и операции

- Карточка показывает предупреждение при активной подписке и объясняет
  результат второй проверки при приостановке.
- Platform проверяет лимит для обоих пакетов и сохраняет собственные
  сроки виджетов.

### Изменения контрактов и миграции

- Admin API и Platform V1 передают необязательный seats_warning.
- Миграция Platform 000029 хранит два наблюдения и номера проверок.
  Команда смены лимита сохраняет номер последней принятой проверки.

### Результаты проверок

| Проверка | Результат |
| --- | --- |
| AccountsFlow, TypeScript, ESLint, Prettier | 15 тестов и проверки прошли |
| Генерация клиента Platform V1, ссылки документации | прошли |
| TestManagerClientWorkspaceAcrossOwnerBoundary с -race | прошёл |
| TestPlatformAccountSubscription и TestPlatformDailyChecks с -race | прошли |
| Platform 000029 up/down на PostgreSQL 17 | два цикла со старым пакетом |

Регрессия с опережением часов Core на 20 секунд воспроизводила предупреждение
сразу после смены лимита. После исправления прошли оба сценария расхождения
на 20 секунд и проверка дубликата после сброса. Интеграционный прогон
PostgreSQL 17 с `-race` также включал `TestPlatformAccountProfileAcrossReplicas`
и `TestPlatformManagerAcrossReplicas`.

### Инструкция запуска и демонстрационный сценарий

- [Локальный запуск](../runbooks/local-run.md).
- На тестовом аккаунте выставьте лимит ниже наблюдаемого числа
  пользователей. Вызовите два успешных обновления данных.
  Проверьте, что после первого пакет активен с предупреждением,
  а после второго приостановлен.

### Происхождение данных демонстрации

Тесты используют синтетические аккаунты, пакеты и наблюдения.
