## A. Admin API: большие списки

### Методика

`load_benchmark_test.go` генерирует данные программно, без БД:
N аккаунтов, у аккаунта `i` от 1 до 5 подключений (`i%5+1`), состояния
распределены детерминированно: 70 % active, 10 % reauth_required,
8 % disabled, 5 % error, 4 % pending, 3 % uninstalled; webhook
(80/8/5/4/3), authorization, `RecentFailedJobs` и гранты
`lead-status`/`activity` коррелируют с состоянием. Данные подаются в
`accounts.New([]adapter.Backend{fixture.New(...)}, nil)`.

Сценарии (подбенчмарки `BenchmarkListAccountsLarge`):

- `filtered` — прямой путь списка с фильтром поиска (`Q`, домен
  `load-501`), `ListFilter{Limit: 25}`;
- `scan_status` — путь сканирования с пост-фильтром
  (`Connection=reauth_required`), `maxScanAccounts=1000`;
- `get_account_5_connections` — `GetAccount` для аккаунта ровно с
  5 подключениями.

Команда и окружение:

```text
make bench-admin
docker ... golang:1.25-alpine go test -run '^$' \
  -bench 'BenchmarkListAccountsLarge' -benchtime=3x -count=1 \
  ./internal/accounts/
```

`goos=linux`, `goarch=arm64`, в контейнере доступно 2 CPU
(`GOMAXPROCS=2`). Каждый подбенчмарк вызывает `b.ReportAllocs()`.
В обычном `go test` бенчмарки не запускаются, `make test` setup не
платит.

Составной прогон пакета: `ok ... 2.165s` (все шесть сценариев);
`make bench-admin` целиком — 16.6 s wall clock, из них ~14 s —
скачивание Go-модулей в чистый контейнер.

### Выводы A

- Прямой фильтр-поиск масштабируется линейно: 3.9 мс → 43.9 мс на
  10⁴ → 10⁵ аккаунтов, ~1.3 КиБ памяти на аккаунт (клон fixture).
- Путь с пост-фильтром в 7–8 раз дороже: 30.6 мс → 332.5 мс;
  `scanAccounts` клонирует и перечитывает весь fixture на каждую
  страницу скана (до 10 страниц по 100 записей).
- `GetAccount` с 5 подключениями: 2.7 мс → 33.3 мс; стоимость — клон
  всех данных и линейный поиск в fixture, у Core-адаптера будет
  индексный запрос.
- Числа — верхняя оценка стоимости CPU/аллокаций Admin API на
  fixture; реальный Core-адаптер делает SQL-запросы и сетевые вызовы.

## B. Core admin read: EXPLAIN

### Методика

Pilot-стек Core уже запущен. Использована scratch-БД `admin_load_check`
в контейнере `amocrm-activity-postgres-1` (postgres:17-alpine,
PostgreSQL 17.10). Живые БД (`amocrm_core`, `amocrm_activity`,
`amocrm_events`) не читались и не изменялись; контейнеры не
останавливались.

Порядок в одной оболочке с `trap` на удаление:

1. `CREATE DATABASE admin_load_check`;
2. миграции Core по порядку: `migrations/000001..000017`.
   Миграции `migrations/activity` и `migrations/crmevents` не
   применялись: `internal/adminread` читает только core-БД
   (installations, integrations, oauth_credentials, jobs,
   job_attempts, audit_log, integration_services, activity_pilots,
   installation_webhook_destinations, activity_command_*,
   lead_status_*); таблицы `settings`, `panels`, `command_receipts`,
   `crm_events` живут в отдельных БД Activity/CRM Events и доступны
   Core через service API, а не SQL;
3. `deploy/fixtures/load-core-installations.sql` (insert-only,
   ~10 s); в начале файла guard: скрипт отказывается работать, если
   `current_database()` не `admin_load_check`;
4. `ANALYZE` + `VACUUM (ANALYZE)`;
5. `EXPLAIN (ANALYZE, BUFFERS)` каждого запроса дважды (run 1
   «холодный», run 2 «тёплый»); в отчёте — run 2;
6. `DROP DATABASE admin_load_check` через `trap` (сработал даже при
   ошибке загрузки), проверка:
   `SELECT count(*) FROM pg_database WHERE datname='admin_load_check'`
   → `0`.

Запросы взяты из `internal/adminread/store.go` и `stats.go`; лимиты
`26` (`limit 25 + 1`) и `101` (`limit 100 + 1`), курсоры — реальные
значения последней строки первой страницы. Запросы перечислены в
порядке отчёта:

1. список аккаунтов, count без фильтра;
2. то же, `status='reauth_required'`;
3. страница аккаунтов (GROUP BY + ORDER BY max(updated_at));
4. то же, `status='reauth_required'`, limit 101;
5. то же, keyset-курсор (HAVING);
6. детали аккаунтов, `account_id IN (26 id)`;
7. список установок, первая страница;
8. то же, `status='active' AND webhook_status='error'`;
9. то же, keyset-курсор;
10. список jobs: `status='failed'`, `created_at >= now()-7d`;
11. список jobs: `status='queued'`, без окна;
12. jobs summary: `GROUP BY status`;
13. stats: подключения `GROUP BY code,status`;
14. stats: события периода (`audit_log` за 7 суток);
15. stats: активные аккаунты (OR + EXISTS по jobs);
16. stats: ошибки jobs за 7 суток;
17. stats: latency `avg`/`p50` по `job_attempts`;
18. stats: очереди за 7 суток `GROUP BY type,status`;
19. stats: `count(*)` с `status='reauth_required'`;
20. stats: `sync_problems` (outbox × receipts);
21. stats: `max(updated_at)` по installations/jobs;
22. stats/accounts: count для `auth_problems`;
23. stats/accounts: страница для `auth_problems`;
24. audit: страница без фильтра;
25. audit: `action='installation.authorized'` + курсор;
26. audit: по `installation_id`.

  scan по jobs/installations/job_attempts.

  внешняя сортировка 2.7 MB на диск.

  индексы (`audit_log_cleanup_idx`,
  `audit_log_action_created_idx`,
  `audit_log_installation_created_idx`) с Incremental Sort по `id`.
- № 19 — Index Only Scan по `installations_status_idx` (1.4 мс).
- № 8: до правки корреляции fixture фильтр `status='active' AND
  webhook_status='error'` возвращал 0 строк; после декорреляции
  webhook-статуса — 26 строк за 0.28 мс по `installations_status_idx`
  с остаточным фильтром.

### Проверка индексов-кандидатов (только scratch)

Отдельная серия: scratch-БД пересоздана, загружены те же данные,
созданы ровно четыре предлагаемых индекса, `ANALYZE`, затем те же
запросы (курсоры пересчитаны) прогнаны повторно. Улучшения
(warm, было → стало):

| Индекс | Запрос | Было, ms | Стало, ms |
| --- | --- | ---: | ---: |
| installations (updated_at, id) | № 7 список установок | 33.6 | 0.36 |
| installations (updated_at, id) | № 9 курсор установок | 39.0 | 0.44 |
| jobs (status, updated_at, id) | № 10 status+since | 13.6 | 0.93 |
| jobs (status, updated_at, id) | № 16 ошибки jobs | 26.6 | 2.13 |
| jobs (updated_at, type, status) | № 18 очереди | 38.9 | 20.0 |
| jobs (updated_at, type, status) | № 21 last use (jobs) | 42.6 | 0.46 |
| job_attempts (finished_at) + duration_ms | № 17 latency | 38.8 | 15.4 |

Селективность подтверждена планами: № 7 и № 9 перешли на
`Index Scan using load_installations_updated_id_idx` (26 строк без
сортировки), № 10 — на `load_jobs_status_updated_id_idx`, № 16 —
Index Only Scan по нему же, № 17 — Index Only Scan по индексу
`job_attempts`, № 18/№ 21 — Index Only Scan по
`jobs (updated_at, type, status)`.

Серия с индексами шла при более высокой нагрузке хоста: planning
time у всех запросов 2–8 мс против 0.4–2 мс в базовой серии, а
например № 14 дал 70.6 мс против 35.2 мс без изменений плана.
Поэтому абсолютные «стало» — ориентир; надёжный сигнал — выбор
индекса в плане.

Наблюдение-предупреждение: `jobs (updated_at, type, status)` делает
для № 12 (jobs summary) привлекательным параллельный Index Only Scan
вместо seq scan; в сериях с индексами он дал 43–47 мс против 33.9 мс
в базовой. Перед миграцией Core это стоит перепроверить на реальном
объёме; при необходимости индекс можно сузить/исключить.

В первой (расширенной) серии также проверялись индексы, которые
добавлять не стоит:

- `jobs (status)`: № 12 jobs summary 33.9 → 43.3 мс (Index Only Scan
  дороже seq scan на 200 тыс. строк);
- `installations (account_id, updated_at DESC)`: № 1 count 21.8 →
  67.7 мс, № 3 страница 26.5 → 70.4 мс, № 5 курсор 27.5 → 56.4 мс;
- `installations (integration_id) INCLUDE (status)`: № 13 33.9 →
  36.0 мс (выигрыша нет).
- № 15 не лечится индексом: остаётся ~195 мс при seq scan
  installations; кандидат — переписать SQL на Core (разделить OR на
  два запроса/CTE), это вне этого репозитория.

Атрибуция — по имени индекса в плане; в серии с четырьмя индексами
они создавались одновременно, изолированных замеров «ровно один
индекс» нет.

### Недостающие индексы (предложение, Core migration не применялась)

Точный текст, если решение будет принято на стороне Core:

```sql
CREATE INDEX installations_updated_at_id_idx
    ON installations (updated_at DESC, id DESC);

CREATE INDEX jobs_status_updated_at_id_idx
    ON jobs (status, updated_at DESC, id DESC);

CREATE INDEX jobs_updated_at_type_status_idx
    ON jobs (updated_at, type, status);

CREATE INDEX job_attempts_finished_at_idx
    ON job_attempts (finished_at) INCLUDE (duration_ms);
```

Важно: ни один из этих индексов не создавался в `amocrm_core` или
любой другой живой БД; миграций в `amocrm-pro` этот репозиторий не
добавлял. Изменения на стороне Core оформляются отдельным ADR/PR с
повторной проверкой записи (индексы замедляют jobs INSERT/UPDATE).

### Ограничения измерений

- один хост, общий контейнер с живым pilot-стеком; scratch-БД
  удалена, живые БД не трогались;
- данные полностью синтетические, распределения и корреляции
  приближены к ожидаемым, но не к реальному трафику;
- кэш тёплый (`shared read=0`), холодный диск/IO не измерялись;
  run 1 и run 2 различаются в пределах шума, в отчёте run 2;
- план зависит от статистики после `ANALYZE`, версии PostgreSQL и
  селективности; замеры — одна серия, без оценки разброса;
- бенчмарки Admin — Docker `linux/arm64`, 2 CPU, fixture-адаптер
  (клон данных на каждый вызов), не Core-адаптер;
- кандидатные индексы проверялись совместно в одной scratch-БД.
