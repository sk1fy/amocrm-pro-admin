## Замечания

### 1. [P1] Кеш предыдущего сотрудника доступен после повторного входа

Место: [LoginPage.tsx](../../frontend/src/features/auth/LoginPage.tsx),
строки 25–27. Связанные места:
[router.tsx](../../frontend/src/app/router.tsx), обработчик 401;
[EmployeesPage.tsx](../../frontend/src/features/system/EmployeesPage.tsx).

После 401 приложение открывает форму входа, не очищая QueryClient.
Успешный вход заменяет только `keys.me`; данные сотрудников и сессий
предыдущего пользователя остаются в кеше. Обычный logout очищает кеш,
но истечение сессии обходит этот путь.

Браузерное воспроизведение: администратор открывает список сотрудников,
уходит со страницы, сессия истекает; повторное открытие сотрудников
получает 401. После входа как viewer запрос сотрудников получает 403,
но экран одновременно показывает «Недостаточно прав» и прежнюю таблицу
сотрудников администратора. Это реальное раскрытие данных через UI,
несмотря на работающую серверную проверку прав.

Исправление: отменять запросы и очищать данные прежнего пользователя
на границе авторизации либо разделять кеш по идентификатору сотрудника.
При 403 защищённые сохранённые данные также не должны оставаться на экране.

### 2. [P1] Production принимает публичный токен Core admin по умолчанию

Место: [config.go](../../../amocrm-pro/internal/platform/config/config.go),
строки 115–120. Источник значения:
[docker-compose.yml](../../../amocrm-pro/docker-compose.yml), строки 83–84;
аналогично в Activity и v0 compose.

Compose всегда включает admin listener и подставляет опубликованный
development-токен при отсутствии `ADMIN_API_TOKEN`. `LoadAPI` проверяет
парность адреса и токена, но не запрещает этот токен вне development.
Таким образом, запуск с `APP_ENV=production` и корректными остальными
секретами успешно поднимает API с заранее известной авторизацией.
Любой клиент с сетевым доступом к listener сможет читать admin-данные.
Публикация host-порта на loopback ограничивает доступ, но внутри Docker
listener слушает все интерфейсы и токен остаётся самостоятельной защитой.

Изолированный тест `TestReviewRejectPublicAdminTokenInProduction`
подтвердил отсутствие ошибки при такой конфигурации.

Исправление: запрещать известный development-токен вне development;
для production требовать явно заданный секрет либо оставлять listener
выключенным до явной настройки.

### 3. [P2] Фильтр продукта не соответствует значениям каталога

Место: [service.go](../../backend/internal/accounts/service.go),
строки 497–505. Связанные места:
[AccountsPage.tsx](../../frontend/src/features/accounts/AccountsPage.tsx),
строки 86–99; [backends.yaml](../../deploy/backends.yaml).

Каталог и выпадающий список предлагают продукты `lead-status` и
`activity`. Сервер сравнивает их с `Connection.IntegrationCode`, где
находится код OAuth-интеграции: например, `fixture-widget-a`, а не код
сервиса. Поэтому выбор существующего продукта даёт пустой список.

Воспроизведение на `fixture.Demo`: без фильтра — 6 аккаунтов; присутствуют
7 грантов `lead-status` и 1 грант `activity`. Оба фильтра возвращают
0 аккаунтов. Проблема не ограничена fixtures: код интеграции Core
и код подключённого сервиса являются разными сущностями.

Исправление: согласовать семантику продукта в каталоге, запросе и сервере.
Если фильтр означает сервис, передавать и проверять фактические гранты;
если интеграцию — наполнять варианты фильтра кодами интеграций.

### 4. [P2] История аккаунта обрывается после первой страницы источника

Место: [service.go](../../backend/internal/accounts/service.go),
строка 367; аналогичная потеря продолжения admin-аудита — строка 397.

`History` запрашивает у каждого источника только первые `limit` записей,
не передаёт исходный курсор и игнорирует полученный `NextCursor`.
Пагинация затем выполняется только внутри уже загруженного фрагмента.

Воспроизведение: одно подключение с 26 записями аудита, `limit=25`.
Адаптер возвращает 25 записей и курсор продолжения; история аккаунта
возвращает те же 25 записей с `next_cursor=null`. Последняя запись
недоступна. Для нескольких подключений продолжение может появиться,
но старые записи за первой страницей каждого источника всё равно теряются.

Исправление: сохранять курсоры источников и обеспечивать продолжение
объединённой истории, а не повторно фильтровать первые страницы.

### 5. [P2] Операции аккаунта не показывают следующие страницы задач

Место:
[AccountOperationsPage.tsx](../../frontend/src/features/operations/AccountOperationsPage.tsx),
строки 37–42 и 114.

Для каждого подключения загружаются первые 50 задач, максимум 100 при
изменении размера страницы. `search.cursor` и все ответные `next_cursor`
игнорируются; `JobsTable` не получает параметры продолжения.

Браузерное воспроизведение: при URL с `cursor=older-jobs-page` запрос
содержит только `?limit=50`. Ответ имеет `next_cursor`, но кнопки
«Дальше» нет. Задачи за первой страницей нельзя открыть из операций
аккаунта, даже если они хранятся в Core и доступны через API.

Исправление: реализовать пагинацию объединённого списка, хранить её
состояние в URL и передавать продолжение таблице.

### 6. [P2] Карточка аккаунта теряет факт ошибок фоновых задач

Места:
[types.go](../../../amocrm-pro/internal/adminread/types.go),
строки 55–62 и 74–85 (`AccountInstallation` / `InstallationSummary`);
[map.go](../../backend/internal/adapter/core/map.go),
`mapAccountListItem` / `mapCardSummary`.

Core возвращает `recent_failed_jobs` для установок в списке аккаунтов,
но не передаёт его в карточках установок, используемых `GetAccount`.
Admin API при сборке карточки не запрашивает этот факт дополнительно.
В результате `RecentFailedJobs` равен нулю и `job_failures` исчезает
из `problems` при переходе из списка в карточку. Агрегированное состояние
также может стать благополучнее, чем в списке.

Подтверждено чтением пилотного Core без изменения данных:

| Fixture-аккаунт | Ошибки в списке | Поле в установках карточки |
| --- | ---: | --- |
| 91000006 | 1 | отсутствует |
| 91000002 | 2 | отсутствует |
| 91000001 | 1 | отсутствует |

Исправление: передавать одинаковый факт ошибок в list/detail контракте
и сохранять его в адаптере. Тестировать согласованность списка и карточки.

### 7. [P2] Карточка аккаунта снимает признак непроверенной авторизации

Место: [dto.go](../../backend/internal/httpapi/dto.go), строка 272;
связанный адаптер сохраняет в summary только состояние авторизации.

Core отдаёт `authorization.unverified=true`, поскольку на этапе 1
не выполняется внешний запрос к amoCRM. `toAccountCard` создаёт новую
`adapter.Authorization` только из `State`, обнуляя `Unverified`,
`CredentialsPresent` и остальные факты. Frontend использует `unverified`
для подписи на вкладках «Обзор» и «Виджеты», поэтому предупреждение
пропадает и состояние `valid` выглядит подтверждённым.

Изолированный тест DTO получил:
`state=valid credentials_present=false unverified=false`.
Чтение пилотного Core подтвердило исходное `unverified=true`.

Исправление: переносить фактическое наблюдение авторизации через все слои;
не создавать отсутствующие булевы факты значениями `false`.

### 8. [P2] Таймаут получения попыток показан как отсутствие попыток

Место: [JobsTable.tsx](../../frontend/src/features/operations/JobsTable.tsx),
строки 45–47.

При таймауте Core Admin API штатно возвращает HTTP 200 с наблюдением
`freshness=unavailable`, ошибкой источника и отсутствующими данными.
Компонент проверяет только ошибку HTTP-запроса и заменяет отсутствующие
попытки пустым массивом.

Браузерное воспроизведение: задача имеет `attempts=2`; при раскрытии
приходит недоступное наблюдение. UI пишет «Попыток нет», без сообщения
о недоступности источника и кнопки повтора.

Исправление: отображать ответ через `Observation` либо явно обрабатывать
`freshness` и ошибку наблюдения до проверки пустого массива.

### 9. [P2] Нефильтрованный список возвращает total=0 при отказе Core

Место: [service.go](../../backend/internal/accounts/service.go),
строки 122–140.

`totalKnown` начинается с `true`. `Gather` исключает ошибочные результаты
из `Items`, поэтому отказавший источник не попадает в цикл, который мог
бы сбросить этот флаг. Для одного недоступного Core API отвечает
`items=[]`, `sources.status=unavailable`, но `total=0` вместо `null`.
При частичной доступности количество доступных записей также выдаётся
как полное. Ветка со включённым постфильтром обрабатывает этот случай
правильно; существующий integration-тест проверяет именно её.

Подтверждено `TestReviewUnavailableTotal` с
`fixture.Unavailable("core")` и пустым `ListFilter`.

Исправление: учитывать ошибки всех источников при определении известности
итогового количества, в том числе без фильтра.

### 10. [P2] Карточка подключения скрывает новые доставки Activity

Место: [delivery.go](../../../amocrm-pro/internal/activitybridge/delivery.go),
строка 352. Вызывающий код:
[connections.go](../../backend/internal/httpapi/connections.go), запрос
`ListConnectionDeliveries` с `Limit: 10`.

Новый admin-путь использует `ListDeliveriesFiltered` без ограничения
на ошибки, но сохраняет сортировку от самых старых записей, унаследованную
от операторского CLI. После появления 10 старых успешных доставок
последующие команды, в том числе ошибочные, не попадают в карточку.
Курсора продолжения у этого ответа и интерфейса нет.

Интеграционное HTTP-воспроизведение на отдельном PostgreSQL: 10 старых
`accepted` и новая `failed`. Ответ с `limit=10` содержит только старые
успешные доставки, новая ошибка отсутствует.

Исправление: для карточки выбирать последние доставки либо реализовать
продолжение списка; отдельно сохранить ожидаемый порядок операторского CLI.
