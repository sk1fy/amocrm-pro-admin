# Распределение: диагностика и восстановление

РС-09, локальная версия. Подробная Core семантика:
[Core runbooks](../../../amocrm-pro/docs/runbooks/).

## Запуск и демонстрация

`make check` запускает проверки в Docker с отдельными тестовыми БД.
Fixture E2E: `make e2e`; вымышленные аккаунты 91000001–91000006,
UI E2E: аккаунт 91000002, установка
`f1a00000-0000-4000-8000-000000000004`. Это синтетический адаптер, видна метка «тестовые данные». Он не вызывает amoCRM.

1. Войти и открыть аккаунт → виджет → «Распределение сделок».
2. Сверить observed_at, origin, доступность источника и null/0.
3. Найти operation UUID из строки; проследить событие и результат.
4. Для blocked результата раскрыть безопасные поля и «Повторить доставку».
   message_id — отдельный UUID, row id может быть составным.
5. При outcome_unknown, applying/in_flight или confirming/settled —
   «Проверить результат назначения». Команда
   только запрашивает свежий CRM GET; не запускает новое назначение.
6. Проверить 202 operation, её результат и отдельно trace назначения.
7. Приостановить новые назначения и обновить summary; очередь TeamOS и
   ранее принятые эффекты сохраняются. Возобновление — явная команда.

## OAuth, webhook и отставание

При auth_error/reauth_required нужна повторная OAuth авторизация владельца
аккаунта. Не передавать токены в комментарии/лог/fixture. Проверка доступа
— POST «Проверить подключение», не GET страницы.
Webhook repair — существующее «Восстановить подписку». При отсутствии
capability/timeout — восстановить доступность внутреннего Core listener,
проверить конфигурацию без вывода секретов, обновить наблюдения.
Backlog events/results и oldest_pending_at — Core outboxes, не очередь
TeamOS. Unknown/stale/unavailable не означают отсутствия работы.

## Неизвестный результат

Остановить новые назначения выбранной установки, выяснить результат
существующей операции. Не удалять guard/claims, не редактировать SQL и
не создавать новый requestId для повторного PATCH. Если GET не даёт
достаточного подтверждения, сохранить unknown и передать оператору.
Blocked delivery повторяется лишь по frozen message_id/CAS attempts.
Командная квитанция не заменяет проверку результата назначения.

После перезапуска операция может остаться в `applying` или `confirming`.
Для этих незавершённых состояний тоже доступна проверка существующего
результата: её 202 ещё не подтверждает назначение. Если версия успела
измениться, обновить цепочку и проверить актуальный результат.

## Другие окружения

1. Изолированный сервер + CRM fixture: проверить сеть, TLS/private ports,
   health, timeout, роли, backup/restart и восстановление outboxes.
2. Тестовый сервер + тестовый amoCRM аккаунт: OAuth/re-OAuth, webhook,
   установленный ZIP, 2–3 сотрудника и искусственные сделки. Проверить
   trace и результат в amoCRM, TeamOS и виджете; рекомендованный вариант.
3. Локальные сервисы + HTTPS tunnel + тестовый аккаунт: быстрый live
   smoke при доступном ноутбуке. Внешне публиковать только callback/widget
   API, admin listener оставлять private.

Для живой приёмки нужны согласованные версии, тестовый домен/сервер,
интеграция и отдельные аккаунты; production не используется. Серверные
метрики Core: backlog/age/state/error, без account/user IDs в labels.
Реальное переключение/откат старого распределителя — отдельный РС-10.

РС-10: [контроль пилота](lead-distribution-pilot.md) и ссылки на каноническую приёмку.
